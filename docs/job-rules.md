# Job rules, matcher, sources and fetcher

The map of the code that finds adverts, decides whether one may be shown as a Critical Skills job, and saves the result: where each rule lives, the order the rules run in, what the fetcher writes, and how it is all proven. Read it before you change a rule, the matcher, a source adapter or the fetcher. Words follow `GLOSSARY.md`. Numbers like #95 are entries in the decision log.

The rules, the rules matcher and the adapters are a port of a Python prototype that ran on real adverts from 5 November 2026 and was hand-checked. That code behaves exactly like the Python on purpose, quirks included. Every known quirk has a test whose name starts with `known quirk:`. Fixing a quirk is a product change: do it alone, name its decision, and expect that test to change. Where the code now differs from the Python on purpose, a comment starting `NEW BEHAVIOUR` says what was measured (the input limits, the scam wording rule, and three rules found by the gate on 10 November 2026: "must be a national of an EU member state" counts as no sponsorship, maternity cover counts as a contract under two years, and pay written as "€80,000/yr" is read as yearly pay instead of being dropped as a revenue figure). Four more rules came from the gate on 11 November 2026: "FTC" and student placements or interns in the title count as a contract under two years (`readers/contract.ts`); "must be eligible / authorised to work in Ireland", a requirements line that is only "Right to work in Ireland" and LinkedIn's "Work authorisation: Ireland (required)" count as no sponsorship (`readers/wording.ts`); and an advert that says the post "can be based in any of the following offices:" with a place outside Ireland in the next lines is not Ireland only (`irish/location.ts`). The plain words "right to work in Ireland" are deliberately not a rule: they also come in "or the ability to obtain it". The AI matcher, the gate and the fetcher are new work with no Python behind them.

## Packages

| Package | What it does | Main exports |
|---|---|---|
| `@portal/sources` | One adapter per kind of job site. Each returns adverts in one shape (`RawAdvert`) | `fetchGreenhouse`, `fetchAshby`, `fetchSmartRecruiters`, `fetchWorkday`, `fetchAmazon`, the career-site readers `fetchPhenom`, `fetchSitemap` and `fetchSalesforce` (W1c), the type `SourceAdapter`, and `runLinkedin` |
| `@portal/matcher` | Reads a title and advert text and gives the occupation code, whether it is on the Critical Skills list, and a confidence | `rulesMatcher`, `TITLE_RULES`, the type `Matcher`, `createAiMatcher`, `chatClient`, `scoreGate` |
| `@portal/rules` | The readers (salary, contract, wording, doctor grades), the employer code (name cleaning, big-company brand, agency, public pay tier, duplicate keys, name suggestion), the Irish check, and the decision chain | `assess`, `INPUT_LIMITS`, and each reader |

| `@portal/fetcher` | Takes adverts from the adapters, runs each through `assess`, and saves the result | `runBoards`, `planAdvert`, `atsTasks`, `hashAdvert` |

Rules, matcher and sources touch neither the database nor the network: every outside thing is passed in. The fetcher is handed a database pool and the boards to read, and only its one entry file reads the environment. An adapter is given the fetch function, the board and the ids already known, and returns every id it saw plus full records for the new ones. It throws `FetchFailedError` when a fetch failed and returns empty lists when a board is truly empty: the difference decides later whether jobs may be closed.

## The order of the rules (`assess` in `packages/rules/src/chain`)

`assess(advert, data)` takes one advert and the data the rules need (the cleaned DETE employer names, the public pay-deal names, the matcher) and returns one `Assessment`: a stage, a bucket and what was read. The order is part of the behaviour. A third argument, `StaffInput`, is for the admin queue only (#166): `contractConfirmed` stops the "contract unclear" and the two #95 stages from stopping the chain (a short contract still does), and `salary` stands in for what the salary reader finds. The fetcher never passes it.

1. **Input limits.** An advert over a limit (title 300, employer 200, location 500, employment type 100, salary box 1,000, description 30,000, counted in code points) is not assessed and gets the stage `0 advert too long (admin queue)`. This is the one thing the Python does not do. Adverts are untrusted text, and three ported patterns slow down with the square of the input length.
2. Flags: agency by name, "sponsorship available", scam wording (a request for money from the candidate: "pay a fee", "send a deposit", "registration fee"). A match is dropped when it is an employer's own warning against scams ("we will never ask candidates to pay a fee", "against our policy", "no agency will ask") or a benefit ("registration fees paid"): on 10 November 2026 the plain pattern matched 101 of 1,310 saved adverts and every one was such a warning or a benefit. The chain itself does nothing with the flag; the fetcher sends a flagged advert that would pass to the admin queue.
3. Location looks Irish, or stage `3 not in Ireland`. Since decision #149 (11 November 2026) it must be Ireland only: a location that also names a place outside Ireland ("Dublin or London", "Kilkenny / Quincy, Massachusetts") gets no badge, Northern Ireland counts as outside, and so does an advert text that says the post "can be based in Dublin or London". Several Irish places and remote Ireland stay in. The word lists are in `packages/rules/src/irish/location.ts`; the old Python test is kept there as `locationLooksIrish` for the parity run.
4. "No sponsorship" wording, or stage `4`.
5. Occupation from the matcher: not recognised is stage `5`, not on the list is stage `6`, low confidence is the admin queue. "Not on the list" is tested before "low confidence".
6. Contract length: under 2 years is stage `7`, unclear is the admin queue.
7. Salary: below the minimum, a range crossing it, or none stated without a big-company brand, each stage `8`. Otherwise a pass.
8. A test posting overrides all of the above (stage `0 test posting`).
9. The Irish employer check by evidence, skipped when the stage already starts with `3` or `4`. "Unsure" goes to the admin queue only for a pass or a stage `8`.
10. Doctor grades with no 2 years stated, and "permanent / specified purpose" (#95), for a pass or a stage `8`.
11. The public pay tier, the bucket, whether an AI step would read the advert, and the sector. The sector follows the Python (`run_day.py`: health, IT, construction and engineering, finance, pharma and science, other) plus two it does not have (#257): `care` (SOC 6145, 6146, 6147, 1242) and `hospitality` (5434, 5435, 5436, 1221, 1223, 1224, 9272, 9273, 9274), in `packages/rules/src/chain/sectors.ts`. A pharma employer still gives `pharma and science` first. On those codes the chain no longer matches the Python, on purpose (the parity run expects the new sector there).

## The AI matcher and the 98% gate (`packages/matcher/src/ai`, `src/gate`)

The launch gate (#79, #145): of the jobs passed with a Critical Skills badge in a frozen, labelled test set of at least 300 adverts, at least 98% must truly qualify. The share of rejected jobs that were rightly rejected is reported beside it and is not a gate.

- **The AI matcher** (`createAiMatcher`) has the same type as the rules matcher, so the chain can use either. It sends only the title and the description (#119), between markers, cut to a stated length. The model answers with a code, one entry id from the two occupation lists it was given, a confidence and a quote. The code, not the model, decides list membership from that entry, and the answer is checked strictly. The quote counts as found when it is exact or close: a quote of at least 6 words that matches a stretch of the advert with at most 20% of its words added, missing or changed (case and punctuation ignored); a shorter quote must be exact. A bad answer, a model error or a timeout is never a pass: the advert goes to the admin queue. No model is named in the code: the address, the key and the model id are passed in.
- **The gate** (`scoreGate` and the runner) puts every advert of the test set through the real `assess` and scores the badge. The runner refuses a set that does not match its frozen hash, keeps every model answer so a stopped run goes on later, and writes a report with numbers and ids only. `packages/matcher/src/gate/README.md` has the file formats and the two commands: the rules matcher alone as a baseline (no key, no network), or a model.
- **The AI as a second opinion** (`createBatchChecker`, `applySecondOpinion`, `keepsBadge` in `packages/matcher/src/ai`): the rules chain runs first, unchanged, and only adverts that end with a badge go to the model, up to 10 in one request, each with an id (A1, A2, ...). Each answer is checked with the same strict check against its own advert only; a missing, repeated, malformed or unquoted answer queues that advert, and an unreadable reply is asked for once more. A badge stays when stated pay is over 68,911 and the model's pick is not on the Ineligible list, or, for lower or unstated pay, the pick is on the Critical Skills list with medium or high confidence. Otherwise the job moves to the admin queue (stage "5 unsure occupation"), never dropped. The gate runs this with `PORTAL_GATE_MATCHER=rules+ai`.
- The test set, the occupation lists and the reports live in the private data folder, never in this repo. The labels are made blind, from the advert and the DETE rule texts only (#120).

## The fetcher (`packages/fetcher`)

`runBoards` reads each board, a few at a time (Workday one at a time, see below), and handles each advert on its own, so one bad advert or board never stops the run. `planAdvert` is the pure part: one assessment becomes the rows to write.

| The chain says | What is saved |
|---|---|
| Passed on stated pay or the big-company rule | A live job with the badge, its text and search data, and the advert row |
| Unsure, public pay, or scam wording on a pass | A job in the admin queue with its text (the database trigger adds the review item) |
| Rejected, or over the input limits | The advert row only: result, stage, short evidence. Never the advert text (#122) |
| A badge the model disagrees with | A job in the admin queue (stage `5 unsure occupation`), no badge, the model named in `matcher_model` |
| A badge the model could not check (budget used up, model error, timeout) | Nothing. The advert comes back next run |

- **The AI second opinion:** a run first assesses every new or changed advert with the rules chain, then sends the badge ones to the model (`applySecondOpinion`), `batchSize` a request (default 10), then writes. The run has a request budget, `maxModelRequests`, shared by all boards; badge adverts past it, in a failed batch, or after the deadline are not written and are listed in `unsaved`, so the next run reads them again. Batches are per board, so a run makes at most one part-empty request more per board than `ceil(badges / batchSize)`. A badge is saved only when the model backed it. `laptop.run.ts` needs `FETCHER_MODEL_URL`, `FETCHER_MODEL_KEY`, `FETCHER_MODEL_ID`, `FETCHER_MAX_MODEL_REQUESTS` and `occupation-lists.json` in the private data folder.
- **An unknown employer** becomes an unclaimed organisation with an alias name. The name key is computed in SQL with the database's own cleaning, never in TypeScript. Companies staff have checked are loaded before with their brand and DETE names by the company seed (docs/database.md, "Company seed"), so their adverts find them instead.
- **A known advert** carries a hash of its text. Seen again with the same hash it costs no write. Changed, it is assessed again: a live job gets its new content, goes back to the admin queue if the rules are now unsure, or closes as `recheck_failed` if it now fails, with its text deleted. Boards whose list call carries the text are compared every run, the others one day in seven.
- **An advert that is gone** from a fetch that worked and returned ids is marked gone, and its live job is closed and its text removed. A failed fetch, or an empty answer from a board with known adverts, closes nothing. An advert that comes back is assessed again, and a job the fetcher closed is reopened if it passes.
- **Staff's jobs are never touched:** a job in review or hidden, or one staff closed, keeps its status and text whatever the advert does.
- **Being gentle with the boards (W1, 18 Nov 2026).** Every Workday company is one domain behind one Cloudflare rate limit, which answered HTTP 429 to every Workday board from 16 Nov. Every wait is in `PACE` (`packages/sources/src/ats/shared.ts`). Workday boards (`serial` in `atsTasks`) run one at a time in their own lane, 1.5 s apart, beside the 8-way pool of the other kinds, and the calls of one Workday board are 0.3 s apart. `makeCaller` tries a 429 or 503 up to 3 times in all, waiting what `Retry-After` says (seconds, or a date counted from the response's `Date`) or else 5 s then 15 s; one wait is at most 60 s, one board's waits at most 90 s, and the whole run's at most 180 s (one budget shared by every board), and past a budget the call gives up at once. After 2 Workday boards in a row give up on 429 or 503, the rest of them fail without a request ("skipped after repeated 429"). A failure's text names the status, the tries, the `retry-after`, `cf-ray`, `cf-mitigated` and `server` headers and the first 200 characters of the body (one chunk read at most, control characters removed); it lands in `fetch_run.error`, cut to 300. A Workday detail refused for the rate limit fails the board (skipping it would leave a known posting unseen, and closed). A Workday posting whose one list location (`locationsText`) is not Irish gets no detail call; "2 Locations" or none still does. The requests carry an honest `User-Agent` (`IrishWorkPermitJobs/1.0`) and `Accept-Language`. Worst case added to a run: 180 s of waits plus 19.5 s of pauses between boards plus 0.3 s a Workday call.
- **A red run (W1).** `laptop.run.ts` fails (exit code not 0, so GitHub emails the owner) when `runFailure(reports)` says every board of one kind failed or more than half of all boards did. It decides after every board is saved and closed; the workflow's later steps (`!cancelled()`) still run. The fetch watch and the guard read `fetch_run`, not the run's colour, so a red run with some good boards still counts as "a fetch worked today" and the watch starts its one retry per slot as before.
- **Workday is left out (W1b, 18 Nov 2026).** The first live run of the W1 fix (GitHub Actions run 44262644215) showed Workday's Cloudflare answering GitHub's runners `HTTP 429` with `cf-mitigated: challenge` and an HTML challenge page: a bot challenge for data-centre addresses, not a rate limit, so no wait or retry helps. A one-request test from Vercel's Dublin region got the same challenge; the engineer's own laptop got 200. Getting past the challenge (scripted browsers, proxies) is ruled out, and a laptop runner was rejected (the laptop is not always on). So the daily fetch sets `FETCHER_SKIP_KINDS: workday` until the employers' own career sites (sitemaps and schema.org `JobPosting`, W1c) replace it. `main.ts` reads `FETCHER_ONLY_KINDS` or `FETCHER_SKIP_KINDS` (comma lists, at most one set; both unset is every kind) and `kindFilter` (`src/boards.ts`) keeps those tasks from `atsTasks`; both set, an unknown kind, or no board left refuses to start. A board not in the run is not read and gets no `fetch_run` row; its live jobs close after 7 days through the stale-board close below. The guard and the watch leave Workday out (`docs/database.md`). `runFailure` judges only the boards in the run.
- Every statement is a constant with parameters, an advert's writes are one transaction, and no network call is made while a transaction is open. The budgets are counted statements, held by tests: 4 a board, 1 a rejected advert, 6 a job with a known employer, 9 with a new one.
- **Eight Workday employers from their own career sites (W1c and W1e, 18 Nov 2026).** `packages/sources/src/careers/careers.ts`, research in the planning folder (`step15/w1c-careersites.md`). Each kind reads what the site itself publishes for search engines and job sites, from one host per board, `PACE.siteCallGapMs` (2 s) between two calls of a board, the same `User-Agent`, the origin lock, the 32 MB body cap and the 429/503 retries of `makeCaller`:
  - `phenom` (Mastercard, Thermo Fisher, State Street, Abbott): `POST https://<site>/widgets` with the body the site's own search page sends (per site `lang`, `country`, `pageId` in `boards.json`; read them from `phApp.ddo` on `/search-results` if a site changes), the Ireland country filter, pages of 50 until `totalHits`. Then one page per job not in `known` (`<path>/job/<reqId>/<title slug>`), read for its JSON-LD `JobPosting`. The filter also lists jobs that name Ireland among many places (Thermo's UK jobs with "Remote, Ireland"): a job whose listed `country` is another is dropped before its page, and a job whose `JobPosting` has no place with an Irish `addressCountry` (Ireland, IE, IRL) after it. `/widgets` is the sites' internal search call, not a documented feed, and may change without notice: the board's run then fails red ("unexpected response shape") and nothing closes.
  - `sitemap` (Citi, Fidelity): `/sitemap.xml` (a sitemap index is walked one level deep, at most 20 files and 100,000 URLs, more fails the board), the URLs that match the board's Irish pattern (Citi `/job/dublin/...`, Fidelity `/ie/jobs/<id>/`), then each page's JSON-LD `JobPosting` (Fidelity writes the script type as `application/ld&#x2B;json`, so the attributes are decoded first). Fidelity's URL number is the Workday id, so a known id costs no page call. Citi's URL number is not (the Workday id is the `JobPosting` identifier), so Citi reads its Irish pages (about 30) every run and saves only the new ones.
  - `salesforce`: one GET of `https://a.sfdcstatic.com/digital/xsf/careers/prod/jobs_2.json` (the file Salesforce's careers page loads: every job, about 11 MB, with its full text); rows whose `Countries` has Ireland. No page calls, so it re-reads every day like Greenhouse (`REREAD_DAYS` 1); `phenom` and `sitemap` re-read one day in 7, like Workday.
  - `eightfold` (Applied Materials, W1e, 18 Nov 2026; research `step15/w1d-sources.md`): `GET https://careers.appliedmaterials.com/api/pcsx/search?domain=appliedmaterials.com&query=&location=Ireland&start=<n>&sort_by=relevance`, paging `start` by the page's length (10) until `data.count`, at most 50 pages (more fails the board). The location filter also lists jobs of many places, so a job is kept only when its `locations` has an Irish entry (`Leixlip,IRL`); the location is those places only (`Leixlip, Ireland`). Then one `GET /api/pcsx/position_details?position_id=<id>&domain=appliedmaterials.com&hl=en` per job not in `known`, for `jobDescription` (HTML, through `text()`). The id is `eightfold:amat:<displayJobId>`, the R-number Workday shows (`R2614187`). The advert URL is built as `<origin>/careers/job/<id>` from the numeric id, never taken from the reply (`publicUrl` is ignored). A detail call that fails keeps the job seen but saves nothing; one refused for the rate limit fails the board. This is the site's own search call, allowed by its `robots.txt` (`Disallow: /` with `Allow: /api/pcsx`), not a documented feed: if it changes, the board fails red and nothing closes. It re-reads one day in 7.
  - One JSON-LD reader for all six page sites (`jobPosting`, `readPosting`): the first `JobPosting` of at most 20 `ld+json` blocks (in a list or `@graph` too), title and description through `text()` (Phenom escapes its HTML once more, so it is unescaped first), the Irish places as the location, `employmentType`, `identifier`. A page that fails or has no posting saves nothing; for `phenom` and Fidelity it still counts the job as seen, so a bad page closes nothing (Citi cannot tell its id without the page, so there a job whose page fails is unseen that day and comes back on the next good read). A page refused for the rate limit fails the board.
  - The ids are the employers' requisition ids, the ones Workday shows, so the saved Workday rows were moved to the new kinds once (`packages/db/src/workday-move-cli.ts`, `docs/database.md`) rather than saved twice (Applied Materials joined `MOVES` in W1e: run the move again before the first fetch that reads `eightfold`, or its Workday rows stay twins). The 14 Workday boards stay in `boards.json` (still skipped); the other six (Pfizer, Workday, KLA, Intel, Analog Devices, Medtronic) have no usable own source yet, so their Workday jobs close through the stale-board close below, as do Workday rows the move left behind.
- **Stale-board close (W1c, 18 Nov 2026).** After the boards, `main.ts` runs `closeStale` (`src/store.ts`, one statement `CLOSE_STALE`, as `app_fetcher`): every live fetched job whose board (`job_source`) has had no good fetch for `STALE_BOARD_DAYS` (7, a constant like the other fetcher periods; a board that never had one counts from the advert's `first_seen_at`) closes with close reason `source_stale` (migration 0035, fetched jobs only), its search vector cleared and its text deleted as for an advert gone, and its advert marked gone. That covers the skipped Workday boards, a board dropped from `boards.json`, and a board whose fetch has failed for a week (for example a Phenom site that changed its `/widgets` call). Exactly 7 days is not yet stale. In review, hidden and staff-closed jobs are never touched. When the board fetches well again and lists the job, the advert comes back with its text (it was gone) and the usual reopen brings the job back to live (`source_stale` is in `FETCHER_CLOSED` and job_guard's reopen list); a job it no longer lists stays closed. Budget (`packages/db/test/perf/stale-close.perf.ts`): 760 pages a day when nothing is stale (budget 1,500), 8,005 for closing 280 jobs (budget 60 a job), on 100,000 adverts and 20,280 jobs.
- **The real run** is `packages/fetcher/run/laptop.run.ts`, the only file that reads the environment, with its own config so `npm run check` never calls a job board: `FETCHER_DATABASE_URL=... FETCHER_BOARDS_FILE=... PORTAL_PRIVATE_DATA=... npx vitest run --config packages/fetcher/vitest.run.config.ts`. It runs daily on GitHub Actions (`.github/workflows/daily-fetch.yml`, 05:17 UTC, with a backup slot at 06:02 UTC, or by hand from the Actions tab; a scheduled run first asks `packages/db/src/fetch-guard-cli.ts` whether a fetch already worked today in UTC and skips the fetch if so, and does not fetch if it cannot tell, so a dropped first slot is covered without a second full run) against the live Supabase database as `app_fetcher`, at most 30 model requests and 25 minutes a run, every board but Workday's (`FETCHER_SKIP_KINDS: workday`). Its inputs are in `packages/fetcher/data/` (the boards, DETE 2026 names, public-employer list, occupation lists, and Supabase's public CA certificate; no advert text). The connection is TLS checked against that certificate (`DATABASE_CA_CERT`); a local run against the test database sets `DATABASE_SSL=disable`. `docs/database.md` has the tables, the fetcher's rights and the guards that hold them.

## Rules data still in code

The salary minimum (40,904, a parameter with that default), the big-company brand list, the place lists, the wording patterns and the 66 title rules are constants beside the rule that uses them, each with the Python line it came from. They move to rules tables in a later step. Those tables are not designed yet.

Health registration bodies (S6, decision #269) stay in code for good: `packages/rules/src/registration.ts` holds NMBI, the Medical Council, CORU, PHECC and the PSI (name, steps for an applicant trained outside the EU, official link, `readOn`, `reviewOn` six months later) and the occupation code to body map, read on each body's own site on 19 November 2026 (`step15/s6-registration-bodies.md`). `registrationFor(code, title)` gives `required`, `may_need` or `not_open` (psychologists, 2212, register expected 2027), or null. The mixed codes 2217, 2219 and 2112 look at the title, lower-cased and padded as the matcher does: a CORU-regulated title (radiographer, dietitian, medical scientist) gets CORU's steps, a known unregulated one (physiologist, audiologist, perfusionist, other scientists) nothing, any other the cautious line. The public job read (`GET /api/job`) and occupation read (`GET /api/occupation`, code only) return it as `registration`; nurses and midwives also get the "degree or diploma accepted by NMBI" note. The daily reminders (`scheduled-checks-cli.ts`) open one `registration_body_review` item for rules data editors when a body's `reviewOn` has come; change the content and both dates in one PR.

## How it is proven

- **Repo tests** (part of `npm run check`): made-up text only, every branch, every known quirk, a time budget per package, and hostile input (1 MB adverts, very long lines, odd Unicode, script tags, lying page counts, redirects to another host).
- **The rules as data (#229):** every runtime path takes the minimums, the occupation lists, the public pay employers and the big-company names from a `RulesSnapshot` (`packages/rules/src/snapshot.ts`): the chain through `ChainData` (`chainRules(snapshot)`), the checker, the second opinion, the posting check and the occupation page. The constants in `thresholds.ts` and the lists in `employers/brand.ts` are version 1. The apps call `getRules()` (`current.ts`, once per process); the daily fetch builds the snapshot with `rulesFromFiles(PORTAL_PRIVATE_DATA)` and `checkSnapshot` refuses an empty list or a missing minimum before any board or database request. On 13 November 2026 every parity count and the rules-only gate were the same before and after the change. The stage texts that name a figure ("8 salary below €40,904", "8 range crosses €40,904 (no rule yet)", "7 contract under 2 years") are written from the minimums the check used (16 November 2026), so with version 1 they read exactly as the Python wrote them.
- **Keeping the lists current (D5):** the weekly DETE watch (`packages/db/src/dete-watch-cli.ts`, `docs/database.md` `dete_watch`) opens a `dete_page_changed` staff item when DETE's notices page, either list page or either Word list changes; staff then change the rules through `/api/rules` (two people). Nothing updates the rules by itself.
- **General permit posts and exceptions (16 November 2026, feature plan 4.2):** the employer post takes `permitType` (`critical_skills` by default, or `general`) and `exceptionConfirmed`. A General post (`rulesFor` in `apps/portal/lib/jobs.ts`) has no occupation list or contract length, is refused for a full quota (`generalQuotaFullCodes`), needs stated pay at `general` (EUR 36,605) or `generalLower` for the codes in `generalLowerCodes` (6145), and always needs the sponsorship statement. The four General fields of the `minimums` kind are optional, all or none; version 1 has none, so a General post is refused with `GENERAL_RULES_NOT_SET` until a version has them (the figures are `GENERAL_*` in `thresholds.ts`). An Ineligible entry whose title says "with the exception of" passes for both permit types when `exceptionConfirmed` is true; otherwise the refusal carries the title as `exception`. The tick is not stored. A condition the Ineligible titles do not name is in `CONDITIONS` (`apps/portal/lib/jobs.ts`, audit row P6, 18 November 2026): code 6145 (care workers and home carers) needs the same tick that the employer is a care provider, not a private household; the chef conditions (experience, "not fast food") and every "disability services" exception are already in their titles. `POST /api/portal/jobs/check` runs these checks with nothing written, and `GET /api/portal/jobs/suggest` gives up to 3 codes from the matcher's title rules (`suggestCodes`). The daily rules run (`rules-run-cli.ts`) judges a General job against the General minimum.
- **The official SOC 2010 list:** `packages/rules/data/soc2010-unit-groups.json` holds the 369 four-digit unit groups of ONS's "SOC2010 structure" spreadsheet (source URL and licence inside: Open Government Licence v3.0, per the ONS site footer; read 13 November 2026). The occupation lists use these codes (DETE's Levels 3 and 4 of SOC-2010; all 246 are in it). `isSoc2010`, `SOC2010_CODES` and `socTitle` in `packages/rules/src/soc.ts` are the one reader: the employer post, the staff manual post, the pay floor role family, the permit checker (`unknown_code`), the occupation page slug and the candidate profile refuse a code that is not on it. The badge rules, the matcher and the fetch do not read it.
- **Parity runs** (not part of `npm run check`): each package has a `*.parity.ts` test that runs our code and compares it with the Python's own output on 1,310 saved real adverts, field by field. On 10 November 2026 every one showed 0 differences. After the three gate rules above, the readers run shows 131 differences on the saved adverts (27 adverts with EU national wording, 3 with maternity cover, 14 with pay written as "/yr"), the chain run 38 adverts that differ (115 after the Ireland-only rule #149, which turns away 77 more saved rows: 73 by location, 4 by text), and the made-up run 6,791 differences, all from maternity cover or pay with "/yr"; each was checked to come from one of the three rules. The matcher run still shows 0. The four rules of 11 November 2026 raise the readers run to 205 saved adverts that differ (from 131) and 7,612 made-up cases (from 6,791), and the chain run from 255 adverts that differ to 263. They need the private data folder, named by the environment variable `PORTAL_PRIVATE_DATA`, and fail with a clear message without it. The saved adverts are other sites' text, so they stay on the engineer's machine and never enter this repo. Run one with `npx vitest run --config packages/rules/src/chain/vitest.parity.config.ts` (the other configs are beside the readers, the employer code, the matcher rules and the adapters). Since 18 November 2026 the chain run expects every deliberate change since the port from a frozen file in the private folder, `L2/expected-changes.json` beside `reference.json`: for each changed advert its id, the decisions behind it (#149, #150 and #151, #156, #159, PR #25, #257; each named in a `NEW BEHAVIOUR` comment in `packages/rules/src/chain/assess.parity.ts`) and the chain's value for each changed field, with no advert text. The run compares the chain with the Python with those overrides only and fails on any other difference and on any override the chain no longer gives; the scam rule (which may clear a flag, never add one) is the one allowance in code. On 18 November 2026: 265 adverts, 1,701 field values, 0 differences. **The chain parity run must be green before any rules change merges**: run it from the repo root with `PORTAL_PRIVATE_DATA="<private folder>/step5/parity" npx vitest run --config packages/rules/src/chain/vitest.parity.config.ts --disableConsoleIntercept`. After a deliberate rule change, and only then, regenerate the file by adding `PARITY_WRITE_EXPECTED=1` to that command: it refuses to freeze a difference no named change explains (add the new change to `causeOf` first), and the new overrides are checked by hand against the adverts before the change merges. Nothing regenerates it automatically.
- **Fixtures for the adapters** have the structure of real responses, recorded once, with every text value replaced by made-up text.
- **The fetcher** is tested against the real test database as the real role `app_fetcher`, and was run on the real boards on 10 November 2026: 27 of 27 boards, 959 adverts saved in 55 seconds (353 live, 163 in the admin queue, 443 rejected), and a second run that saved nothing new. A later run with the change handling closed one job whose advert had gone and added two new adverts.
- **The gate** was run once as a preview on 10 November 2026, on 128 labelled adverts (too few to be a gate): the rules matcher alone passed 41 jobs with a badge and 40 truly qualified. No model has been run against it yet.

## Known limits

- A description of 30,000 digits still takes about 0.9 seconds in the salary reader. The limit bounds it. Making the pattern itself fast changes behaviour, so it waits for a decision.
- Titles, locations and Ashby descriptions are not stripped of HTML, as in the Python. Whoever shows them on a page must escape them.
- Not ported: Lever, Workable and Recruitee (no board uses them).
- LinkedIn: the adapter is ported (`runLinkedin`, with a retry on 429 and a request budget, both off by default), but its advert page answered 429 in the one recording pass, so its parser has never met a real page. It is not in the fetcher.
- The AI second opinion runs in the daily fetch on a free OpenRouter model set in `.github/workflows/daily-fetch.yml`; the production model is not chosen yet.
- A changed advert that the rules are now unsure about sends its live job back to the admin queue, even if an admin approved it before.
- The same job on two boards is saved twice: there is no cross-source duplicate key yet.
- Three packages each carry their own small helper that gives a JavaScript pattern Python's meaning (`readers/pyre.ts`, `employers/py-text.ts`, `matcher/src/rules/pyRegex.ts`). One shared copy would do.
