# Database

The map of the Postgres schema: roles, rules, tables, retention and callable functions. Read it before you write a migration, a query or a grant.

The files in `packages/db/migrations` are the source of truth once they exist. If this page and a migration disagree, the migration wins and this page is out of date: change it in the same pull request. The full design (60 tables, 11 views, the reasoning and the trial evidence) is a private document, see the last section. Words follow `GLOSSARY.md`. Numbers like #104 are entries in the decision log.

The Drizzle schema in `packages/db/src/schema` is made from the migrations, never written by hand: after changing a migration, run `npm run db:test:up` and then `npm run db:pull`. `schema.test.ts` fails until the two match.

`packages/db/test/rules-snapshot.txt` lists every trigger, CHECK rule, unique rule and app-role right in schema `public`, and `rules-snapshot.test.ts` fails when the database no longer matches it. After a migration that adds, drops or changes any of them, run `npx vitest run --project db packages/db/test/rules-snapshot.test.ts -u`, then read the diff of `rules-snapshot.txt` before committing it. A reviewer sees the same diff in the pull request.

## Roles

One role per deployed app, plus the owner. A bug on one site then cannot reach another side's tables.

| Role | Used by | Reaches |
|---|---|---|
| `portal_owner` | Migrations only | Owns every table, view and function. Never used at runtime |
| `app_candidate` | Candidate site | Candidate tables and its own login pool. Public job and organisation columns. Shared tables only through its views |
| `app_portal` | Employer and agency portal | Its own pool, organisation, jobs, statements, pay floors. Reads membership but never writes it (migration 0009); a team changes only through the team functions (0013). Shared tables only through its views. Nothing on candidate tables |
| `app_admin` | Admin panel | Staff tables, queues, cases, settings. Reads most things. Runs the erase and retention functions |
| `app_fetcher` | Job fetcher and importers | Fetched jobs and adverts, fetch runs, the CRO register. Inserts notifications. Nothing on candidate or staff tables |

There is no fifth role. Erasure and retention run inside database functions. Grants are by column wherever a role sees only part of a table.

Each app role has `statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout` set (migration 0000). These are defaults that stop honest code from holding the database up. They are not a limit: Postgres has no hard cap per role, so a hostile session can lift them with `set statement_timeout = 0` (`side-fixes.test.ts` documents this). Nothing in the database stops a hostile session from doing this, so the timeouts protect against slow honest code only.

## Rules for every table

- **Naming and types:** lowercase singular names, in schema `public`. Functions live in schema `private`. Ids are `bigint` identity, except Better Auth's text ids. Times are `timestamptz`, money is whole euros as integers, statuses are `text` with a CHECK. A CHECK on a column that may be empty is written so that NULL fails it (`is not distinct from` or an explicit `is not null`).
- **No row level security (#124).** A grant picks tables and columns, not rows. "Own rows only" (a candidate's saves, a company's jobs) is held by app code and its tests. The database holds the grants, the per-side views, the trust-column triggers and the clash rules.
- **Per-side views.** `services_case`, `case_document`, `consent_record`, `notification` and `notification_preference` hold candidate and portal rows together. `app_candidate` and `app_portal` get no rights on those five tables. Each gets views of its own side (`candidate_` and `portal_` plus the table name), made `security_barrier` with `check option`. `published_content_page` is the eleventh view.
- **Trust columns.** Columns that carry a claim or a decision (organisation status, big-company flag, `restricted_until`, job source and badge, hidden and in_review moves, pay floor status, block flags) are left out of the portal and fetcher grants. Where a grant cannot limit a value, a trigger checks `current_user`.
- **The acting staff id.** Every staff member connects as `app_admin`, so the admin app runs `set local app.staff_user_id` at the start of each transaction. Triggers on `approval_request` and `strike` refuse any `app_admin` write that has no valid acting id and stamp that id into the decider columns. Those columns are left out of every grant.
- **The two-person rule (#104, #136, #137).** A change on the #104 list takes effect only when it points to an `approval_request` confirmed by someone other than the proposer, and not used before. One trigger function checks this on every table that points to `approval_request`. Every staff role grant is two-person (#136). The confirmer must hold the role the request kind needs (#137).
- **Settings are two-person (migration 0004).** An `app_admin` insert or value change on `setting` needs an active acting id and a confirmed, unused `setting` request whose `change` is `{"value": <the new value>}` (`{"value": null}` for empty). The trigger stamps who and when and writes one `audit_event` row (`setting.change`) with the old and new value. A value is never negative. `app_admin` cannot change `key`, `unit` or the stamps. A migration as `portal_owner` is not blocked.
- **App roles write only their own side (migration 0004).** In `audit_event` each app role may name only its own actor (`app_candidate` a candidate, `app_portal` a portal user, `app_fetcher` a system actor, `app_admin` the acting staff id or a system actor), and `at` is always `now()`. Only `app_admin` and the fetcher write `admin_action`. In `email_outbox` an app role queues only new `pending` rows to its own side (`app_candidate` and `app_fetcher` candidates, `app_portal` portal users or invites, `app_admin` anyone). A `dedupe_key` sent by an app role is stored as `<role>:<key>` in `email_outbox` and `notification`, so `on conflict do nothing` works within a role and no role can take another's key. App code that looks a row up by key must add the prefix. Rows written by the owner's functions keep their key.
- **The public API stays shut.** Supabase's Data API is off. Every migration revokes rights from `anon`, `authenticated`, `service_role` and PUBLIC on tables and functions. Extensions go in schema `extensions`. `pg_graphql` is dropped.
- **Launch B is locked three ways (#72):** a `feature_flag` row; no grants on Launch B tables or functions until a named person runs that migration (#113); and two CHECKs on Launch A tables (`job.application_route = 'own_page'`, `candidate_profile.visible_to_employers = false`) that the same migration drops.
- **Delete actions.** Every foreign key states its delete action. Erasing a candidate cascades to their owned rows and sets null on shared records. A job with saved, tracker, application, case, report or strike rows cannot be deleted. `audit_event` and `email_outbox` hold person ids as plain text with no foreign key, so a log row never blocks a deletion.
- **Paging (#125):** next and previous only, keyed on the sort key plus `id`. Never `OFFSET`. Counts stop at 200. Every list query lives in the Search module and names its columns (never `select job.*`). The Search module is `packages/db/src/search.ts`: `listJobs` (three sorts: sponsor, newest, salary; opaque cursors; the first page carries the capped count) and `getJob` (one live job with its advert, employer, badges, last checked and the rules date). The key rolls over on 1 January only when the refresh next runs (an import or a link change).
- **The fetched-job admin queue (#166 to #168)** is `packages/db/src/admin-queue.ts`, run as `app_admin`: `listQueue(db, staff, { after })` (open and claimed `fetched_job` items, oldest first, next-page cursor) and `getItem(db, staff, id)` (one item with its advert text), both of which refuse a staff member who is not active or lacks `fetched_job_reviewer` (step 13d, #234 D7), `claim`, `release`, `approve` and `reject`. A claim older than 24 hours, or held by someone no longer active, is taken over by the next `claim`; `release` gives an item back to open (claimer only). Each takeover and release writes one audit row (`fetched_job.take_over`, `fetched_job.release`). Each action takes the acting staff id, refuses it unless it is an active `staff_user` holding the `fetched_job_reviewer` role (checked in the same statement, no other role stands in; refusal `not_active_staff` first, then `not_reviewer`, #193), and sets `app.staff_user_id` for its transaction. Only the claimer decides, under row locks on the item and the job. Approve re-runs `assess` on the saved title, employer, county and advert text with the staff member's occupation code (and pay and contract, if given); only a `stated_pay` or `big_company` pass with no scam wording goes live, with the columns the fetcher writes. Reject closes the job as `removed`. Each decision writes one `admin_action` audit row (`fetched_job.approve` or `fetched_job.reject`, a reason code, no free text).
- **Periods are settings.** Nothing stores a delete date. `run_retention` works dates out from `setting`. The audit log period is the one exception.
- **Pooler.** Apps connect through Supabase's transaction-mode pooler: pass no statement name (`prepare: false`), use no `set` without `local`, no advisory locks, no `listen`.
- **Login pools (#97).** Candidate, portal and staff each have their own Better Auth tables, renamed with `modelName` and with camelCase fields mapped to lowercase. Added status columns are declared with `input: false`, and Better Auth does not enforce them, so the Identity module refuses suspended, blocked, disabled and deleted people on every request. Rate limits are stored in the database. Staff sign-up is off.
- **Staff login (#169 to #172).** The admin app serves the staff pool at `/api/auth/staff/*` (`apps/admin/app/api/auth/staff/[...all]/route.ts`) and connects with `DATABASE_URL`, the `app_admin` login. It also needs `STAFF_AUTH_URL` (the admin site's https address; http only for localhost) and `STAFF_AUTH_SECRET` (at least 32 random characters); a request with either missing or bad fails closed. Every admin call starts with `requireStaff(headers)` from `apps/admin/lib/staff.ts`: it refuses no session and anyone whose `staff_user.status` is not `active`, even with an open session, and returns the staff id the admin queue functions take. A staff session ends after 8 hours without use (Better Auth's `expiresIn` 8 h, `updateAge` 5 min, so it ends 7 h 55 min to 8 h after the last use); candidate and portal sessions keep Better Auth's defaults. Staff email is not set up yet, so a reset request sends nothing. The first logins are made by the owner with `DATABASE_URL_MIGRATE=... node packages/db/src/staff-seed-cli.ts <email> "<name>" <role>[,<role>...]`, which asks for the password twice without showing it (at least 12 characters) and, in one transaction as `portal_owner`, writes the `staff_user`, its credential `staff_account`, the roles with `seeded_by_owner = true` and one `staff.seed` audit row. It refuses an existing email, an unknown role and any login that cannot act as `portal_owner`.
- **Candidate login (#174 to #178).** The candidate app serves the candidate pool at `/api/auth/candidate/*` (`apps/candidate/app/api/auth/candidate/[...all]/route.ts`, no pages yet) and connects with `DATABASE_URL`, the `app_candidate` login. It also needs `CANDIDATE_AUTH_URL` (`http://localhost:3000` for now) and `CANDIDATE_AUTH_SECRET` (at least 32 random characters); either missing or bad fails closed. Email goes to the fake sender in `packages/auth/src/fake-email.ts`: it keeps each email in memory (tests read the link), prints the link to the terminal, and refuses to start for any address but localhost or 127.0.0.1, so a deploy cannot quietly send nothing until a real email service is wired in. Sign-up needs `needsPermit`, `over18` and `acceptsTerms`, each exactly `true`; a plugin checks them before the route runs (so an existing email is refused the same way as a new one), and a database hook writes one `consent_record` (purpose `signup_terms`, the current text, the answers in `details`) through the `candidate_consent_record` view inside Better Auth's own sign-up transaction, so no account exists without it. Sign-up refuses with 503 while no `signup_terms` text exists. Save the placeholder wording once, with two different staff ids (the proposer holds any role, the confirmer is an administrator): `DATABASE_URL=<app_admin connection> node packages/db/src/signup-terms-cli.ts <proposer staff id> <confirmer staff id>`; it makes the approval request, confirms it as the other person, saves the text `placeholder-2026-11-12`, and is safe to run twice. With `--portal` first (`node packages/db/src/signup-terms-cli.ts --portal <proposer> <confirmer>`) it saves the employer and agency placeholder instead (purpose `portal_signup_terms`, same version name); each purpose is checked on its own. A candidate session lasts 7 days (Better Auth's default). **Google sign-in (#179)** is on only when both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set (read from the environment, never from a file in the repo); with either missing the Google routes answer "provider not found". Its redirect address is `http://localhost:3000/api/auth/candidate/callback/google`. The client sends the three answers as `additionalData` on `POST /api/auth/candidate/sign-in/social` (`{"provider":"google","callbackURL":"/","additionalData":{"needsPermit":true,"over18":true,"acceptsTerms":true}}`). For a new person the user-create step reads them back from Better Auth's sign-in state and runs the same `checkSignup` as email sign-up (missing or wrong answers: no account, no consent row, redirect to the error address with `error=SIGNUP_ANSWERS_REFUSED`); it also refuses an email Google has not verified (`EMAIL_NOT_VERIFIED_BY_PROVIDER`), and a Google account is created email-confirmed. The consent row is then written by the same account-create hook, inside the same transaction. A person who already has a candidate account signs in without answers and no second consent row is written. Account linking is Better Auth's safe default, written out in `createAuth`: Google joins an existing email-and-password account only when Google says the email is verified and that account's email was confirmed here; an unconfirmed account is not joined (`error=account_not_linked`), and no provider is trusted on its own word. Only the candidate pool has Google.
- **Employer and agency login (#184 to #191).** The portal app serves the portal pool at `/api/auth/portal/*` (`apps/portal/app/api/auth/portal/[...all]/route.ts`; email and password only, no Google, #190) and connects with `DATABASE_URL`, the `app_portal` login. It also needs `PORTAL_AUTH_URL` (`http://localhost:3001` for now) and `PORTAL_AUTH_SECRET` (at least 32 random characters); either missing or bad fails closed. Email goes to the same fake sender as the candidate pool; the email must be confirmed before sign-in (#54), and a session lasts 7 days (Better Auth's default, #189). Sign-up needs `acceptsTerms`, exactly `true` (#188, #194): a plugin checks it before the route runs (so an existing email is refused the same way as a new one, `SIGNUP_ANSWERS_REFUSED`), and the `portal_consent_record` row (details `{"acceptsTerms":true}`) is written in the sign-up transaction, on the newest `portal_signup_terms` text, so a failed write undoes the login. With no such text sign-up answers 503 `SIGNUP_TERMS_MISSING`. Every portal call starts with `requirePortal` (`packages/auth`), which refuses no session and a blocked or deleted login and returns the active membership with its organisation, or `membership: null` for a login with no company; such a login can only become a company's owner, through `POST /api/portal/claim` `{"organisationId": n}` (calls `claim_organisation`: `verified` when the email domain is that company's `organisation_domain` and no other's, otherwise `pending_review` plus an `account_review` item) or `POST /api/portal/register` `{"kind": "employer" | "agency", "displayName", "croNumber"?, "wrcLicenceNumber"?}` (calls `register_organisation`, always `pending_review`). Both take the user id from the session only, refuse any unknown field, a body over 2,048 characters and an `Origin` that is not the portal's own, allow 5 calls in 10 minutes per login, and answer refusals with short codes (`BAD_ORIGIN`, `BODY_TOO_LARGE`, `BAD_REQUEST`, `NO_SESSION`, `REFUSED`, `EMAIL_NOT_VERIFIED`, `ALREADY_IN_A_COMPANY`, `ORGANISATION_NOT_AVAILABLE`, `NUMBER_ALREADY_REGISTERED`, `TOO_MANY_REQUESTS`). The ban check happens there, at claim and registration time, not at sign-up (#191): a banned email domain or company number gets the plain `REFUSED` a blocked login gets, so the reply names no ban. A company-number ban can still be inferred when claiming: the ban check comes before the "is it unclaimed" check, so for a company that is not unclaimed the reply is `REFUSED` if its number is banned and `ORGANISATION_NOT_AVAILABLE` if not (register behaves the same with `NUMBER_ALREADY_REGISTERED`). The email-domain ban cannot be probed this way. The codes are unchanged; changing them waits for an owner decision.
- **Teams (#52, #103, #130, #132, migration 0013).** `GET /api/portal/team` returns the caller's team: every active member sees the members (name, email, role, signer switch); only the account owner also sees open invites (with their expiry) and join requests; a login with no company gets `{"team": null, "joinRequest": ...}` (its own open request, or null). `POST /api/portal/team` takes `{"action", ...}`: `invite` `{email, role, isSigner}` (owner; role viewer, poster or recruiter), `accept` `{token}`, `request` `{organisationId}`, `approve` and `refuse` `{membershipId}` (owner, a join request), `remove` `{membershipId}` (owner, a member or an invite), `leave` `{}` (a member, or a login withdrawing its request), `role` `{membershipId, role, isSigner}` (owner), `transfer` `{membershipId}` (owner). It makes the same checks as claim and register in the same order (portal `Origin`, 2,048-character body, unknown fields refused, session) and allows 20 team calls in 10 minutes per login. `accept`, `request` and `leave` work for a login with no company. The invite makes 32 random bytes, sends the link `PORTAL_AUTH_URL/team/accept?token=...` through the portal's email sender (the fake one until 8.1b) and passes only the sha256 to `team_invite`, all in one transaction, so a failed send leaves no invite (`EMAIL_FAILED`, 502). Refusal codes: `BAD_ORIGIN`, `BODY_TOO_LARGE`, `BAD_REQUEST`, `NO_SESSION`, `REFUSED` (blocked, deleted, banned email domain, or any refusal not listed, #191), `EMAIL_NOT_VERIFIED`, `NOT_OWNER`, `NOT_A_MEMBER`, `MEMBER_NOT_FOUND` (also another company's id), `TEAM_FULL`, `ALREADY_IN_TEAM`, `ALREADY_IN_A_COMPANY`, `INVITE_NOT_VALID` (wrong, used, expired or another email's token, one code for all), `NOT_ALLOWED_DOMAIN`, `OWNER_MUST_TRANSFER`, `VIEWER_NOT_SIGNER`, `ORGANISATION_NOT_AVAILABLE`, `TOO_MANY_REQUESTS`, `EMAIL_FAILED`.

- **Report a job (slice 8.5).** `POST /api/report` on the candidate site and `POST /api/portal/report` on the portal (`packages/db/src/report.ts`, `handleReport`): `{"jobId": "n", "reason": "asks_for_money" | "no_sponsorship" | "job_closed" | "wrong_details" | "other", "evidence"?: "..." (1 to 2,000 characters)}`, the reporter from the session only, the job must be live, 10 reports an hour per login, one open report per login and job. The answer is only `{"ok": true}` or a code (`BAD_ORIGIN`, `BODY_TOO_LARGE`, `BAD_REQUEST`, `NO_SESSION`, `REFUSED`, `TOO_MANY_REQUESTS`, `JOB_NOT_FOUND`, `ALREADY_REPORTED`).
- **Trust and safety (slice 8.5, #44, #91, #104, #134 to #137, #213 to #215).** `packages/db/src/trust-safety.ts`, behind `GET`/`POST /api/trust-safety/reports` and `/api/trust-safety/cases` in the admin app (`requireStaff`, own Origin only, body at most 12,000 characters, unknown fields refused, short refusal codes). Every call needs active staff with the `trust_and_safety` role, checked in the statement that sets the acting id; no other role stands in. Reports: hide the live job at once (`job_hidden`), clear (the job comes back) or uphold (the database closes the hidden job, and a case opens). Cases: open (an `instant_ban` case suspends a verified company and hides its live jobs at once, #213), notify (7-day reply window, notices as `email_outbox` rows to the account owner and the job's poster), enter a reply or appeal received by email or post with its date, decide (cleared; a strike, its level 1 plus the strikes decided in the last 12 months and not overturned, at most 3; or a ban on an instant-ban case, which waits for the 7 days unless marked conclusive). Strike 1 and clearing apply at once; strike 2, strike 3 and a ban are an `approval_request` that a second trust and safety officer confirms, which applies them in the same transaction (strike 2: `restricted_until`; strike 3: `claims_removed_at` and ban rows; ban: ban rows, then the company `banned`). The appeal is decided by one person who neither entered it nor decided the case (for strike 2, 3 and bans the confirmer; the proposer may decide, so two officers are enough, #217); overturned, the database undoes strike 2 and 3 and any ban rows get `ban_lift` requests that a second officer confirms. The WRC report on an agency's instant-ban case is an audit row staff tick off. Audit rows hold codes only.
- **Employer status page (slice 8.6, migration 0017).** `app_portal` has no grant on `strike` (0003 let it read every company's cases and write a reply or appeal on any). `private.status_page(user)` gives any active member the company's state, `restricted_until`, `claims_removed_at`, the strikes decided in the last 12 months and not overturned, and each case once notified or decided (job, reason, notice summary, deadlines, reply, decision, appeal and its result; never the report or any staff id). `private.status_write(user, 'reply' | 'appeal', case, text)` lets only the account owner reply once before `reply_due_at` and before the decision, or appeal once after the decision and before `appeal_due_at` (the case becomes `appealed`); text 1 to 1,800 characters (inside the 2,048-character body cap), no control or format characters but line breaks and tabs; one `audit_event` row of codes. Both run as `portal_owner`, so `strike_guard`'s `app_portal` branch no longer applies and the functions check the windows themselves. Route: `GET`/`POST /api/portal/status` (`apps/portal/lib/status.ts`). Refusals: `status refused: CODE` with `REFUSED`, `NOT_A_MEMBER`, `NOT_OWNER`, `BAD_REQUEST`, `BAD_TEXT`, `CASE_NOT_FOUND` (also another company's case), `ALREADY_REPLIED`, `REPLY_CLOSED`, `ALREADY_APPEALED`, `APPEAL_CLOSED`.

## Tables

Launch A unless marked. "Pool" tables are the five Better Auth tables of a login pool.

### Jobs

- `job`: one advert, whatever its source. `organisation_id` is who stands behind it (strikes fall there, including agency jobs, #89). Status moves draft, in_review, live, under_review, hidden, closed. `permit_type` is required, fetched jobs are always critical_skills (#42). The write guard trigger limits what each role may change, and `posted_at` is set by trigger, never by a role. The fetcher never moves a job back to draft, never changes the close reason of a closed job, and reopens a closed job, to live only, when it expired or the fetcher closed it, as `closed` or as `recheck_failed` (never one staff removed). The close reason `recheck_failed` (migration 0006) is for a live fetched job that fails a later check; a check allows it on fetched jobs only. List indexes are partial on `status = 'live'` and lead with `(not quota_full)`. `permit_history` is copied from the organisation by trigger. So is `sponsor_sort` (migration 0008): the permits DETE issued to the employer in the last 5 calendar years, or -1 with no confirmed DETE link, the first sort key of the default job list (#154, #157), with its own index `job_live_sponsor`. `app_candidate` reads it, no other app role can write it.
- `job_text`: the advert text, kept until the job closes (#122). Also holds the text of a queued fetched advert. A trigger lets `app_fetcher` write text only for fetched jobs and `app_portal` only for employer and agency jobs.
- `job_source`: one row per job board, plus one for portal jobs. Its `last_ok_at` is the "last checked" date, so no job row changes nightly.
- `fetched_advert`: everything the fetcher has seen, rejected adverts included. All nightly churn lives here. Linked only from `job.fetched_advert_id`. `content_hash` is a sha256 hex of the advert as fetched (64 lowercase hex characters or empty, which means assess once more); only the fetcher writes it and only the fetcher and admin read it (migration 0006). A check keeps `stage` to 200 characters and `reason` and `quoted_evidence` to 500, so a rejected advert keeps short evidence and never the advert (#122).
- `fetch_run`: one row per fetch of one source.
- `job_daily_stat`: anonymous views and clicks per job per day (#56).

### Visitors and candidates

A visitor has no table. Their reports and contact messages are rows with no account attached.

- Candidate pool: `candidate_user`, `candidate_session`, `candidate_account`, `candidate_verification`, `candidate_rate_limit`. We add `suspended_at`, `deleted_at`, `last_active_at` and `inactive_warned_at` to the user table. An app role cannot set `last_active_at` more than five minutes ahead of the database clock. Only `erase_candidate` deletes a user.
- `candidate_profile`: details for matching, one row per candidate. Launch B lock: `visible_to_employers` must be false.
- `candidate_cv`: the current CV file record. The file is in private storage, the function returns its key for deletion.
- `saved_job`: a bookmark (#25). Unique per candidate and job. Since 0020 at most 200 per candidate, and only a job that was live at some time (the trigger `private.candidate_job_check`, which `tracker_entry` and `apply_click` also use). "Never live" means draft, in_review, or closed as `abandoned`; a job removed before it went live has the reason `removed` like a live job removed later, so it passes.
- `tracker_entry`: the candidate's record of a job they applied to (#49, #86). Points to the job and copies no job details. On an on-site row a candidate can only set withdrawn, and the trigger checks the old route too, so changing the route in the same update does not get round it.
- `apply_click`: the "Did you apply?" prompt after a redirect (#49). One open prompt per candidate and job.
- `alert`: a saved search that sends email (#25, #77). `created_at` (0024) is when it was made: a never-run alert's new jobs start there. The daily run (`queue_job_alerts`) sets `last_sent_at` on every due alert, and a job is new for an alert when its `posted_at` is after `coalesce(last_sent_at, created_at)`; `posted_at` moves only on the first move into live, so a job that closes and reopens is never sent again (D2).
- `application` (Launch B): an application on our site (#45) with its own copy of what was sent. Erasure and retention empty it and keep job, date and outcome (#133).
- `contact_request` (Launch B): an employer asks a visible candidate for contact (#41, #47). Insert trigger enforces visibility, daily limit and re-ask gap.
- `message` (Launch B): text under an application or an accepted contact request (#98). No thread table, the parent is the thread.
- `candidate_hidden_organisation` (Launch B): companies a candidate hides from (#101, #129).

### Employers and agencies

- Portal pool: `portal_user`, `portal_session`, `portal_account`, `portal_verification`, `portal_rate_limit`. We add `status` (active, blocked), `blocked_at`, `blocked_reason_code`, `last_active_at`, `deleted_at`. Only `erase_portal_user` deletes a user.
- `organisation`: one company page and one team, which can exist before anyone claims it (#129). Triggers tie `status`, `restricted_until`, `claims_removed_at` and `is_big_company` to approved cases and requests (#44, #104). The portal creates and claims only through `claim_organisation` and `register_organisation`. Nothing is deleted, `closed` keeps the row.
- `organisation_name`: legal names and job-site names under an organisation (#30). Nothing merges automatically, admin confirms each link.
- `organisation_domain`: a company's email domains, for the sign-up domain rule (#37) and the ban rule. `created_at` is not writable by any app role (#137).
- `cro_company`: the CRO register, for the first-time sponsor check (#21). It keeps companies with status Normal plus the leaving statuses "Strike Off Listed", "Liquidation" and "Examinership" (about 343,000 of 829,000 rows, decision #207); the status text is trimmed (the file has "Normal " with a trailing space). The columns `company_type` and `county` were added in migration 0014 (#211); county is read from the address lines and is empty for most rows. Loaded weekly by `packages/db/src/registers-cli.ts cro` as `app_fetcher` (`FETCHER_DATABASE_URL`): it finds the file through the CRO portal's `package_show`, streams the zip and CSV, and upserts by `cro_number`. A number repeated in the file keeps the row with the later status date (the earlier row on a tie). Rows no longer in the file get status "Not in latest file" and are deleted after 90 days. A file with fewer than 80% of the kept rows already held is refused before anything is marked. The data is CC BY 4.0, so the CRO must be credited: the text is the constant `CRO_ATTRIBUTION` in `packages/db/src/registers.ts`, which site pages will show.
- `dete_permit_count`: permits per employer name from DETE files, for company pages and the permit history label (#73).
  Loaded and linked by `app_admin` with `packages/db/src/dete-cli.ts` (`DETE_ADMIN_DATABASE_URL=<app_admin login> node packages/db/src/dete-cli.ts import|link <file>`, or `... dete-cli.ts refresh`). `refresh` recomputes every employer's permit history label and sponsor key and prints how many changed; the daily fetch workflow runs it as its last step, so the 5-year window moves on 1 January (decision #164). `import` takes a tab-separated file `dete_name, year, permits, source_file` (yearly totals, no month; one bad line refuses the whole file; the same file again changes nothing; `organisation_name_id` is never touched). `link` takes `organisation_name_id, dete_name` and sets the link on those DETE rows; an unknown name or id is reported and skipped, never guessed. `permitsLast5Years(db, organisationId)` in `packages/db/src/dete.ts` gives the permits of the current and four earlier calendar years (UTC) over every linked name plus the first year with permits, or `null` for "not linked" (not the same as 0). It counts only DETE names an admin linked; a merged-away organisation's names are not followed.
  The monthly import (step 15b, `.github/workflows/monthly-dete.yml`, the 15th at 07:17 UTC or by hand) is `DETE_ADMIN_DATABASE_URL=<app_admin login> node packages/db/src/dete-monthly-cli.ts`. DETE keeps one file per year at a fixed address (`https://enterprise.gov.ie/en/publications/publication-files/employment-permits-issued-to-companies-YYYY.xlsx`) and adds the new month to it. The command downloads this year's file (UTC year; in January also last year's final one, and a 404 for the new year is a green "not published yet"; any other failure is red), only from that host and path, no redirects, 10 MB cap, and refuses a reply that does not start like a zip. `xlsx.ts` reads the first worksheet with Node's own zlib (no dependency; caps on part size, checksum and size checks, nothing else inflated), `dete-monthly.ts` turns the sheet into the import file (employer in column A, the column headed ending in "Total"; zero counts left out; a negative, fractional, huge or text count refuses the file), and `importPermits(db, rows, { replaceYears: true })` loads it so each year totals exactly what the newest file says: a changed count is updated, a name DETE dropped is set to 0 (its link stays), the same file again changes nothing, and a file whose year total is under half of the stored one is refused as cut off. Any refusal happens before the first write. It prints one line per year (employers, new, changed, unchanged, dropped, labels changed). Linking new DETE names to companies stays by hand with `link`. The 2019 and 2020 layouts are not read by it (they never change; they were loaded with the Python script). Names with format characters (zero-width, direction marks, BOM) are refused by `import` too.
  The permit history label (`organisation.permit_history`) and the sponsor key (`organisation.sponsor_sort`, migration 0008), both copied onto open jobs by trigger, are set by `private.refresh_permit_history()` (migration 0007, extended in 0008), which `import` and `link` run before they commit and print the count of changed labels: `has_history` when any linked DETE row has permits in 2019 or later; `first_time` kept as set; otherwise `not_linked`. `private.mark_first_time(organisation_id)` sets `first_time` ("checked DETE, no record found") only for a confirmed employer (big-company list or a CRO number, #73) with no such row. Both run as `app_admin` only. Approving a first-time employer's registration (account review) calls `private.mark_first_time`, so the company and its open jobs get `first_time`; a qualifying DETE row refuses the approval as `has_permit_history` (409). DETE's own 2019 and 2020 company files do not add up (2019 about 1,500 permits short of its stated total), so use them for "any permit", not for counts.
- `wrc_licence`: the WRC licensed agency list (one PDF, no reuse licence), for the staff check only and never shown publicly (#212). Since migration 0014 `app_portal` and `app_fetcher` cannot read it (`register_organisation` reads it as its owner). Loaded by `packages/db/src/registers-cli.ts wrc` as `app_admin` (`WRC_ADMIN_DATABASE_URL`), only when the PDF's ETag or Last-Modified changed (needs `pdftotext` from poppler-utils). The PDF is parsed by word position; the county is the heading above each group. Sanity checks: the row count is within 5% of last time unless `--accept-count-change` is given, every number is EA plus digits, and repeated numbers are reported. `missed_imports` counts the lists a licence was missing from; 2 means "possibly lapsed", shown to staff and never a ban by itself.
- `register_import`: one row per source (`cro`, `wrc`) with the last validator (ETag plus Last-Modified), the import date and the row count. `app_fetcher` and `app_admin` can write it.
- `owner_reassign` (migration 0022, #234 D6): one row per request to make a member the account owner when the owner cannot be reached. The two ticks (`domain_checked`, `cro_checked`) must both be true, `completes_after` is 7 days after `requested_at`, `status` is open, done or cancelled; one open request per company (`owner_reassign_one_open`). `app_admin` reads; only the three `owner_reassign_*` functions write it.
- `membership`: links a portal login to an organisation (#52, #103). One owner per organisation and one active company per login (#130). A viewer never signs. `app_portal` reads it and has no insert, update or delete right (migration 0009): every membership write goes through a `security definer` function: `claim_organisation`, `register_organisation` and the eight team functions of migration 0013 (see Callable functions). `invite_token_hash` holds only the sha256 of the invite token; the token itself is only in the email. `awaiting_approval` is not used yet (an invite is the owner's approval, whatever the invitee's domain). `app_admin` keeps its direct rights, and raises a company's `member_limit` (10 by default) by updating it.
- `sponsorship_statement`: the signed "we will sponsor" statement per job, which strikes hold employers to (#19, #44). One current statement per job. The signer must be an eligible active member. `admin_on_behalf` needs a confirmed approval request (#16, #104).
- `pay_floor`: a pay floor signed by a big-company employer for a role family, never an agency (#82, #100). Becomes active only with a confirmed approval request.

Agency permit employer facts have no table: they sit on the job columns and on `sponsorship_statement` (#23, #36, #89). A client is not an account type.

### Services, staff and admin

- Staff pool: `staff_user`, `staff_session`, `staff_account`, `staff_verification`, `staff_rate_limit`. Only `app_admin` has rights. Nobody signs up, an administrator creates each login. Users are disabled, never deleted. Turning on a disabled login that holds a role needs a confirmed grant (#136). `app_admin` cannot change the email of a login that holds a role: remove its roles first, then grant them again through confirmed requests. The database cannot tell Better Auth's own password and session writes from another staff member's, so the admin build must hold this rule itself: a staff login is created with no usable password and its owner sets one from an emailed link, and no staff member ever sets another's password.
- `staff_role`: which of the seven #104 roles a person holds. Every grant needs a confirmed request unless `seeded_by_owner`. Removing a role is one person's act (#137), and no trigger may guard that delete.
- `services_case`: one permit services request. Open means `status <> 'closed'`, and an open case freezes erasure of the people it names (#99). Candidate and portal sides use their views. A trigger makes the consent records a case names belong to the same person as the case.
- `case_note`: a handler's private note. `app_admin` only.
- `case_document`: a list of uploaded copies, never originals (#50). Files live in private EU storage. A trigger makes a candidate or portal document sit on a case of the same person.
- `case_quote`: a quote and invoice record paid by bank transfer (#84).
- `content_page`: guides, the updates feed and help pages (#55). Terms and privacy pages are consent texts, not content pages. Public read is through `published_content_page`.
- `contact_message`: the contact form and its staff inbox. Keeps the sender's name and email so staff can reply.
- `report`: a complaint about a job, company, message or profile (#38, #102). The reported company never reads this table. The reporter's identity is cleared when the report closes (#99). `app_candidate` and `app_portal` insert only the reporter's own columns (target, reason, evidence text, snapshot; migration 0015), so a report cannot be filed already hidden or decided.
- `strike`: one case against an organisation (false claim, false pay floor or instant ban, #44, #82, #96). Holds the notice, reply, decision and appeal. Triggers stamp the decider and the dates, set deadlines once, and stop one person entering and deciding the same reply or appeal (#134, #135, #136).
- `ban`: the ban list. A row existing means the ban stands. Never updated. Inserted only in the transaction that applies its case, and only for the case organisation's own CRO number, its domains from before the case opened (#137), or the exact lower-case `email_address` (migration 0015, #215) of someone who joined it before the case opened. A company on a free email provider is banned by its CRO number and its people's addresses, never the provider's domain. `claim_organisation` and `register_organisation` refuse a banned address as they refuse a banned domain. Deleting needs a confirmed `ban_lift`.
- `approval_request`: the two-person rule (#104). A proposed change waits here. The proposer cannot confirm. Kinds and the confirmer role each needs are in the trigger. Rows are born pending. Kinds include `setting` (confirmed by an administrator).
- `review_item`: admin work queues with no table of their own, the fetched-job queue included. One winner claims an item. The portal never writes it, triggers and functions do. `app_fetcher` may insert only `scam_flag` items, with only `queue`, `job_id`, `reason` and `detail`.
- `audit_event`: the append-only log of staff actions, data views and security events. No app role can update or delete. Stores allow-listed values only, never names, emails or free text. Retention is below.

### Shared

- `consent_text`: the exact wording of each consent (#90). Never updated or deleted once published. Sign-up terms, the employer and agency sign-up terms (`portal_signup_terms`, migration 0012, #194) and the privacy notice need a confirmed `terms_privacy_page` request.
- `consent_record`: proof of what one person agreed to and when. App roles cannot choose `given_at` (the default `now()` is the proof) and may update only `withdrawn_at`, once, from empty to `now()`. Erasure turns it into bare proof.
- `notification_preference`: choices per category and channel (#54). Rows exist only where someone differs from the default. For a candidate (0020) the category is `job_alerts`, `apply_reminders` or `account`, and `account` is never off; the candidate routes use the `email` channel.
- `notification`: in-app notices, one row per member. Staff have none. A notice to the other side is written by a trigger or function, never by an app role.
- `email_outbox`: emails waiting to send, saved in the same transaction as the action. The address is looked up at send time. Workers claim with `FOR UPDATE SKIP LOCKED`.
- `feature_flag`: switches that keep Launch B off (#72). Only `portal_owner` writes, through a reviewed migration.
- `setting`: every period and limit that is not final. `app_admin` reads and writes `value`, `is_guess` and the solicitor columns. A value change is two-person, and every change is logged by the trigger. Empty means not set, so nothing is deleted automatically.

## Callable functions

All are `SECURITY DEFINER`, owned by `portal_owner`, in schema `private`, with execute revoked from PUBLIC. Each writes its own `audit_event` rows in the same transaction. Trigger functions also live in `private` and are granted to no role.

- `erase_candidate(id, on_request)`: erases a candidate. Refuses (and returns the reason) while they have an open services case or are the target of an open report. Empties applications, turns consents into bare proof, deletes owned rows and login rows, calls `audit_pseudonymise`. Returns the storage keys of files to delete. Executed by `app_admin`.
- `erase_portal_user(id, on_request)`: the same for a portal login. Also refuses an account owner who still has other active members. Executed by `app_admin`.
- `run_retention()`: runs one batch (up to 1,000 rows) of the first retention rule with rows due, and returns that rule's key and how many rows are left. The admin app's scheduled route calls it in a loop, one transaction per call. Rules are listed in `private.retention_rules()`. Executed by `app_admin`.
- `audit_pseudonymise(id)`: replaces a person's id in the log with a random stand-in. Called only by the two erase functions. No app role.
- `audit_purge()`: deletes audit rows older than 24 months. Run by a monthly pg_cron job as `portal_owner`, or by the named person. No app role.
- `approval_request_due()`: returns the approval request ids that retention may delete. Used by `run_retention`.
- `claim_organisation(portal_user_id, organisation_id)`: a verified person claims an existing organisation, in one conditional update. Executed by `app_portal`. Since migration 0016 (#203) it also refuses, with `COOL_DOWN`, the same login claiming the same company within 24 hours of a rejection (the login's removed owner membership and that company's `rejected` account_review item share the rejecting transaction's instant; a claim that lapsed unanswered is not a rejection).
- `answer_review(portal_user_id, note)` (migration 0016, #197): the active account owner of a `needs_info` company sends a note of 1 to 1,000 characters (no control or format characters). It is stored in the company's open account_review item as `detail.answer` and `detail.answered_at` (never in the audit log, #182), the company becomes `pending_review`, and one `organisation.answer_review` audit row of codes is written. A reviewer asking for more again clears the old answer. Refusals: `REFUSED` (not the owner, or a blocked login), `NOT_WAITING` (not `needs_info`, or no open item), `BAD_REQUEST` (the note). Executed by `app_portal`; the route is `POST /api/portal/review-answer`.
- `register_organisation(portal_user_id, kind, display_name, cro_number, wrc_licence_number)`: sign-up for a first-time sponsor or an agency. Always pending review. It cleans the typed number first (CRO: spaces and a leading IE removed, leading zeros dropped; WRC: spaces removed, upper case, EA added to bare digits, #210) and writes the register result into the account review item detail: `register`, `found`, `name_matches` (compared on the normalised name, so "Acme Ltd" matches "ACME LIMITED"), `status` (CRO only) and `possibly_lapsed` (WRC only). A number not in the register still goes to review, marked not found; nothing new is refused. Executed by `app_portal`.
- The team functions (migration 0013), all executed by `app_portal`, each taking the acting login's id from the session. Each locks the organisation row (`for no key update`) and reads its rows again before checking, so two changes to one team run one after the other; `team_accept` and `team_request` also lock the login's row. Each writes one `audit_event` row (`security`, action `membership.<verb>`, codes only, no email). A refusal raises `team refused: CODE`. The limit counts active members, live invites and join requests against `organisation.member_limit` (expired invites are dropped first). Companies that take on people are `pending_review`, `needs_info`, `verified` and `verified_restricted`.
  - `team_invite(user, email, role, is_signer, token_hash)`: the active owner invites an email (not banned, not the owner's own, not a member, a join request or a live invite of this team) as viewer, poster or recruiter; a viewer is never a signer. Expires after 7 days.
  - `team_accept(user, token_hash)`: a confirmed login whose email is the invite's accepts a live invite (not banned, not already in a company, #130). It becomes active with the invite's role and switch; its own join requests elsewhere are dropped.
  - `team_request(user, organisation_id)`: a confirmed login with no membership and no open request asks to join a company that takes on people. Its email domain must be one of the company's `organisation_domain` rows, and not banned.
  - `team_answer(user, membership_id, approve, role, is_signer)`: the owner approves (active, with the role and signer switch the owner picks; a viewer is never a signer) or refuses (removed) a join request; approval rechecks the requester (not blocked, deleted or banned).
  - `team_remove(user, membership_id)`: the owner removes another active member or withdraws an invite.
  - `team_leave(user)`: a member leaves, or a login withdraws its join request. The owner may leave only as the last active member; then the company's open invites and requests are removed too, and the company itself stays as it is (#132).
  - `team_set_role(user, membership_id, role, is_signer)`: the owner sets another active member's role (viewer, poster or recruiter) and switch.
  - `team_transfer(user, membership_id)`: the owner hands ownership to another active member who is not blocked or deleted; the old owner becomes a recruiter and keeps its signer switch.
  - Helpers with no grant: `team_owner` (the caller's active owner membership, after the lock), `team_room` (the limit), `team_audit`, `team_open`.

Plain functions, not `private` ones:

  - `listRules(db, staff)` (`packages/db/src/rules-admin.ts`, `GET /api/rules`): the versions in force, the confirmed ones still to come and the pending proposals with their change (entries added, removed, changed). Any active staff member.
  - `proposeRules(db, staff, {kind, effectiveFrom, data})` (`POST /api/rules` action `propose`): a rules data editor proposes a whole new version from today or later; a new or changed big-company name needs its link, date read and next review date. One pending proposal per kind.
  - `proposeBigFlag(db, staff, organisationId)` (action `propose_flag`, #230): a rules data editor proposes `organisation.is_big_company` on one company, only when one of its names matches a big-company name in force; the existing `big_company_entry` request on `organisation`.
  - `confirmRules(db, staff, requestId)` and `refuseRules` (actions `confirm`, `refuse`): an administrator who did not propose. Confirming writes the version (or sets the flag) in the same transaction; a minimums version queues one `rules_minimums_changed` outbox notice per company with a live or draft employer or agency job, to its account owner.
  - `withdrawRules(db, staff, requestId)` (action `withdraw`): the proposer only.
  - `seedRules(client)` (`packages/db/src/rules-seed-cli.ts`, the owner's command, `DATABASE_URL_MIGRATE`): writes version 1 of every kind from today's constants, `brand.ts` and the two JSON files, effective from 2026-03-01, `seeded_by_owner` and `run_at` set; refuses a second run.
  - `runRules(client)` (`packages/db/src/rules-run-cli.ts`, `app_admin`, daily from `.github/workflows/daily-fetch.yml` after the expiry step): when the minimums version in force today has no `run_at`, live employer and agency jobs that passed on stated pay and are now below the minimum (the posting check's rule, `minimumForHours`) go `under_review` (the employer reads reason `pay_check` through `portal_jobs`), every active pay floor ends as `expired` (#82), and `run_at` is set; a second run does nothing.
- `queue_job_alerts(p_now)` (migration 0024, step 11 part 11b; #236 Q1, D2, D3): the daily alert run, one statement. Due alerts: `active`, the candidate verified, not deleted, not suspended, with the `job_alerts` email setting on (no row means on); `daily` ones when `last_sent_at` is null or before `p_now`'s UTC day, `weekly` ones the same but only when that day is a Monday. New jobs: live, not quota-full, `closes_at` after `p_now`, `posted_at` after `coalesce(last_sent_at, created_at)` and not after `p_now`, matching every filter the alert sets (`occupation_code`, `sector`, `county` equal; `salary_min` against `salary_sort`, and a job with no stated pay never matches a minimum; `badge` equal). Writes one `email_outbox` row per candidate with new jobs (template `job_alert`, `send_after = p_now`, dedupe key `job_alert:<candidate>:<UTC date>`, params `{run_on, alerts: [{alert_id, job_ids}]}`, at most 20 jobs newest first and at most 10 alerts, lowest ids first), sets `last_sent_at = p_now` on every due alert, and writes one `job_alerts.run` audit row. Returns `{alerts_due, candidates_queued, rows_written}`. Executed by `app_admin`.
- `alerts-run-cli.ts` (step 11b, `packages/db/src/`, `app_admin` in `ALERTS_ADMIN_DATABASE_URL`, `.github/workflows/daily-fetch.yml` step "Queue job alerts", after the minimum step and before retention): calls `queue_job_alerts(now())` once and prints one line of counts; exit 1 when the database refuses.
- `companies_staff_check(staff_id, roles, code)` (migration 0022, step 13 part 13c): raises `staff refused: NOT_ACTIVE_STAFF` unless the id is an active staff user, then `staff refused: <code>` unless that user holds one of the roles. The three functions below and the manual posting, merge preview and list calls use it, so a role is checked in the database, not only in the route. Executed by `app_admin`.
- `merge_organisations(staff_id, absorbed, survivor)` (migration 0022, #234 D1): by an account reviewer or a fetched-job reviewer alone. Refused (`merge refused: CODE`): `NOT_FOUND`, `SAME_COMPANY`, `ALREADY_MERGED`, `TARGET_MERGED`, `NOT_MERGEABLE` (rejected, closed, banned or suspended), `KIND_MISMATCH`, `ACTIVE_MEMBERS` (the 0002 trigger `organisation_merge_check` also refuses it), `HAS_APPLICATIONS`. In one transaction it sets `merged_into_id`, moves the names (the DETE links point to them and follow), lifts the survivor's permit history to `has_history` when the names bring a qualifying DETE record, moves the jobs (their poster membership belongs to the absorbed company, so it is emptied) and writes one `organisation.merge` audit row whose `after` holds `name_ids`, `job_ids` and `job_posted_by_membership`, so a merge can be reversed by hand. There is no undo and there are no suggestions. Since 0022 `claim_organisation` (copied from 0016) and `register_organisation` (copied from 0015) refuse a merged-away company (`claim refused: MERGED`, `sign-up refused: MERGED`). Wrapper `mergeCompanies` in `packages/db/src/merges.ts`; route `/api/companies/merge` (POST merges, GET previews the companies).
- `owner_reassign_request(staff_id, membership_id, domain_checked, cro_checked)`, `owner_reassign_complete(staff_id, request_id)`, `owner_reassign_cancel(staff_id, request_id)` (migration 0022, #234 D6, 20b "Account owner leaves"): account reviewers only. The request needs both ticks true, an active non-owner member of an open company whose login is active, and no other open request; it queues one `owner_reassign_notice` in `email_outbox` to the old owner (ids only) and writes an audit row. The completion is refused until `completes_after` (`TOO_EARLY`), when the owner is no longer the one the request named (`OWNER_CHANGED`) or the member is gone; then the old owner becomes a recruiter and keeps the signer switch (`team_transfer`, 0013). Any account reviewer cancels an open request. Wrappers in `packages/db/src/owner-reassign.ts`; route `/api/companies/owner-reassign`.
- Manual posting (`packages/db/src/manual-posting.ts`, #232; migration 0022 adds only the `job_source` row `admin`/`manual` and the index `job_manual_idx`): `createManualPost(db, staff, input)` by an account reviewer inserts a job with source `admin_manual` and `posted_by_staff_id` as `app_admin` (`job_guard` only restricts the portal and the fetcher). It is `live` with badge `critical_skills_eligible` only when the employer post checks pass (list occupation, fixed term of at least 24 months, the rules chain, pay against the minimum for the stated hours with `>=`, nothing held back for review); otherwise a draft, with the reason code in the `job.manual_post` audit row. Never `sponsor_confirmed`. `closeManualPost` closes the staff member's own post; `listManualPosts` pages by id for the account reviewer, trust and safety officer and administrator. Route `/api/manual-jobs`.
- `move_application(application_id, status, membership_id)` (Launch B): moves an application and its tracker row together. `app_portal`, from the Launch B migration only.
- `search_visible_candidates(organisation_id, filters, cursor)` (Launch B): the portal's candidate search. `app_portal`, from the Launch B migration only.

- Step 13d (migration 0023, #231, #233, #234 D2 to D5, D7, D8). Migration 0023 adds the check `pay_floor_role_family_check` (a floor's role family is four digits), the trigger function `private.pay_floor_withdrawn` (a floor that goes from `pending_check` to `withdrawn` drops its open or claimed `pay_floor_check` item to `dropped`, outcome `withdrawn`, in the same statement; it runs with the owner's rights because the employer withdraws as `app_portal`) and the index `audit_event_action_idx (action, at, id)`. It replaces no function. The functions below are plain functions run as `app_admin` with the acting staff id from the session; every call reads the staff member's roles from the database first (`staffRoles`, `requireRole`, which also sets `app.staff_user_id`).
- Staff accounts (`packages/db/src/staff-admin.ts`, routes `/api/staff`, administrators only): `listStaff(db, staff)` (logins with roles and status, and the role grants waiting for a second administrator); `proposeRoleGrant(db, staff, targetId, role)` (an administrator inserts the `grant_role` or `grant_administrator` request; one pending grant per login and kind) and `confirmRoleGrant(db, staff, requestId)` (a different administrator confirms and the role is written in the same transaction; the two halves are `proposeGrant` and `confirmGrant` in `role-grant.ts`, shared with the owner's `role-grant-cli.ts`); `refuseRoleGrant(db, staff, requestId)` (refused by a different administrator, withdrawn by the proposer); `removeRole(db, staff, targetId, role)` (one administrator, at once); `disableLogin(db, staff, targetId)` (status `disabled` and every `staff_session` row of the login deleted in the same transaction; returns `sessionsEnded`); `enableLogin(db, staff, targetId)` (refused with `holds_roles` while the login holds a role, because migration 0004 treats re-enabling a role holder as a role grant: remove its roles, enable it, grant again with the two-person rule). `removeRole` of `administrator` and `disableLogin` first lock the active administrators' `staff_user` rows in id order and count them again, and refuse with `last_administrator` when the login is the only active administrator. Nothing here makes a login; `staff-seed-cli.ts` does. Every action writes one `staff.*` audit row (codes and ids only).
- The audit log viewer (`packages/db/src/audit-read.ts`, route `/api/audit`, GET only): `listAudit(db, staff, { staff, action, objectType, objectId, from, to, after })`, newest first, 50 a page by keyset on `(at, id)`; an administrator reads every row and may filter by any staff member, every other active staff member reads only the rows where they are the actor and is refused another member's id (`not_administrator`). Dates are UTC days (`from` inclusive, `to` inclusive). `app_admin` holds `select` and `insert` on `audit_event` and nothing else.
- The content editor (`packages/db/src/content-admin.ts`, route `/api/content`): `listContentPages`, `getContentPage` (content editor, rules-data editor, administrator); `createContentDraft` and `editContentDraft` (content editor only; kind and slug never change; a published page is withdrawn before it is edited); `publishContent` (a content editor publishes `help` and `update`, a rules-data editor `guide` and `occupation`; the database still wants a source and a checked-on date for all but `help`, mapped to `needs_source_and_checked_on`); `withdrawContent` (content editor, any kind). The writer is stored in `updated_by_staff_user_id`; each write has one `content.*` audit row. Limits: title 200 characters, body 50,000, source link 500 and http(s) only, no control or format characters (a body keeps line breaks and tabs), slug as `validSlug` and four digits for `occupation`.
- The fetched-job queue route (`/api/fetched-jobs`): list, item, claim, release, approve and reject over `admin-queue.ts`. The approve step's rules data is built in `apps/admin/lib/queue-rules.ts` from the fetcher's data files; the step 13 combine points it at the shared rules.
- Email safety (step 15 part 15c, `packages/auth`, no migration; slice 2 review findings 3 to 5): a limit per email address on `/request-password-reset` and `/send-verification-email` for the candidate and portal pools (`emailLimitPlugin` in `packages/auth/src/email-limit.ts`, 3 an hour per address and route, on top of the per-IP limits; one upsert into the pool's `*_rate_limit` table under the key `email:<route>:<HMAC-SHA256 of the lower-cased address>`, whose `last_request` holds the end of the hour so Better Auth's 5-minute prune leaves it; 429 for any address, with or without an account; an address over 254 characters is refused). Sign-up and reset emails are sent after the reply through the app's `background` handler (Next's `after()`), and a failed send is logged with `console.error`. A Google sign-in that joins an existing candidate deletes that candidate's password account and ends its earlier sessions. `outbox-cli.ts` sends `account_deleted` to `params.email`.
- Job alert routes (step 11 part 11a, `packages/db/src/alerts.ts`, no migration; #25, #54, D1, D5, D6, Q2): signed in, `/api/candidate/alerts` (GET list, POST create, PUT `{ id, ...filters }` edit, DELETE `{ id }`), `/api/candidate/alerts/pause` and `/resume` (POST `{ id }`). Filters only, never free text (`search_text` is not written): `occupationCode` (SOC 2010), `sector` (the six rules sectors), `county` (the 26), `salaryMin` (0 to 1,000,000), `badge` (`sponsor_confirmed` or absent), `frequency` (required). At most 10 alerts per candidate, every row counts (`ALERT_LIMIT`); create and resume need a verified email (`EMAIL_NOT_VERIFIED`) and refuse Stamp 4 (`STAMP_4`); another candidate's alert id is `ALERT_NOT_FOUND`. A resume from paused or unsubscribed sets `last_sent_at = now()`, so "new" starts again then. Each alert gets a 32-character `unsubscribe_token` (24 random bytes, base64url) that no signed-in route returns.
- `unsubscribeInfo(db, { token, scope })` and `unsubscribe(db, { token, scope })` (same file, route `/api/alerts/unsubscribe?token=...&scope=one|all`, no sign-in, no Origin check, token only): GET changes nothing and answers the filters in words (`alert: null` for an unknown token); POST (also the RFC 8058 one-click, body `List-Unsubscribe=One-Click`) sets `unsubscribed` on that alert, or on every alert of the same candidate for `scope=all`. A token of the wrong length or characters is refused (400) before any query.
