# Database

The map of the Postgres schema: roles, rules, tables, retention and callable functions. Read it before you write a migration, a query or a grant.

The files in `packages/db/migrations` are the source of truth once they exist. If this page and a migration disagree, the migration wins and this page is out of date: change it in the same pull request. The full design (60 tables, 11 views, the reasoning and the trial evidence) is a private document, see the last section. Words follow `GLOSSARY.md`. Numbers like #104 are entries in the decision log.

The Drizzle schema in `packages/db/src/schema` is made from the migrations, never written by hand: after changing a migration, run `npm run db:test:up` and then `npm run db:pull`. `schema.test.ts` fails until the two match.

The HTTP routes of the three apps (paths, roles, bodies, replies and every error code) are described in OpenAPI files, one per app: see [openapi/README.md](openapi/README.md). A new or changed route updates its file in the same commit.

`packages/db/test/rules-snapshot.txt` lists every trigger, CHECK rule, unique rule and app-role right in schema `public`, and `rules-snapshot.test.ts` fails when the database no longer matches it. After a migration that adds, drops or changes any of them, run `npx vitest run --project db packages/db/test/rules-snapshot.test.ts -u`, then read the diff of `rules-snapshot.txt` before committing it. A reviewer sees the same diff in the pull request.

## Roles

One role per deployed app, plus the owner. A bug on one site then cannot reach another side's tables.

| Role | Used by | Reaches |
|---|---|---|
| `portal_owner` | Migrations only | Owns every table, view and function. Never used at runtime |
| `app_candidate` | Candidate site | Candidate tables and its own login pool. Public job and organisation columns. Shared tables only through its views |
| `app_portal` | Employer and agency portal | Its own pool, organisation (read only since 0031: the profile, logo and close are functions), jobs, statements, pay floors. Reads membership but never writes it (migration 0009); a team changes only through the team functions (0013). Shared tables only through its views. Nothing on candidate tables |
| `app_admin` | Admin panel | Staff tables, queues, cases, settings. Reads most things. Runs the erase and retention functions |
| `app_fetcher` | Job fetcher and importers | Fetched jobs and adverts, fetch runs, the CRO register. Inserts notifications. Nothing on candidate or staff tables |
| `app_backup` | The backup every 6 hours (migration 0026) | Reads every table, view and sequence (`pg_read_all_data`), writes nothing, runs no function. Three connections at most. No password in the migration: the engineer sets it live |

Erasure and retention run inside database functions. Grants are by column wherever a role sees only part of a table.

Each app role has `statement_timeout` and `lock_timeout` set, and every role but `app_backup` also `idle_in_transaction_session_timeout` (migration 0000; `app_backup` is 0026 and keeps its snapshot transaction open while `pg_dump` runs). These are defaults that stop honest code from holding the database up. They are not a limit: Postgres has no hard cap per role, so a hostile session can lift them with `set statement_timeout = 0` (`side-fixes.test.ts` documents this). Nothing in the database stops a hostile session from doing this, so the timeouts protect against slow honest code only.

## Rules for every table

- **Naming and types:** lowercase singular names, in schema `public`. Functions live in schema `private`. Ids are `bigint` identity, except Better Auth's text ids. Times are `timestamptz`, money is whole euros as integers, statuses are `text` with a CHECK. A CHECK on a column that may be empty is written so that NULL fails it (`is not distinct from` or an explicit `is not null`).
- **No row level security (#124).** A grant picks tables and columns, not rows. "Own rows only" (a candidate's saves, a company's jobs) is held by app code and its tests. The database holds the grants, the per-side views, the trust-column triggers and the clash rules.
- **Per-side views.** `services_case`, `case_document`, `consent_record`, `notification` and `notification_preference` hold candidate and portal rows together. `app_candidate` and `app_portal` get no rights on those five tables. Each gets views of its own side (`candidate_` and `portal_` plus the table name), made `security_barrier` with `check option`. `published_content_page` is the eleventh view.
- **Trust columns.** Columns that carry a claim or a decision (organisation status, big-company flag, `restricted_until`, job source and badge, hidden and in_review moves, pay floor status, block flags) are left out of the portal and fetcher grants. Where a grant cannot limit a value, a trigger checks `current_user`.
- **The acting staff id.** Every staff member connects as `app_admin`, so the admin app runs `set local app.staff_user_id` at the start of each transaction. Triggers on `approval_request` and `strike` refuse any `app_admin` write that has no valid acting id and stamp that id into the decider columns. Those columns are left out of every grant.
- **The two-person rule (#104, #136, #137).** A change on the #104 list takes effect only when it points to an `approval_request` confirmed by someone other than the proposer, and not used before. One trigger function checks this on every table that points to `approval_request`. Every staff role grant is two-person (#136). The confirmer must hold the role the request kind needs (#137).
- **Settings are two-person (migration 0004).** An `app_admin` insert or value change on `setting` needs an active acting id and a confirmed, unused `setting` request whose `change` is `{"value": <the new value>}` (`{"value": null}` for empty). The trigger stamps who and when and writes one `audit_event` row (`setting.change`) with the old and new value. A value is never negative. `app_admin` cannot change `key`, `unit` or the stamps. A migration as `portal_owner` is not blocked.
- **App roles write only their own side (migration 0004).** In `audit_event` each app role may name only its own actor (`app_candidate` a candidate, `app_portal` a portal user, `app_fetcher` a system actor, `app_admin` the acting staff id or a system actor), and `at` is always `now()`. Only `app_admin` and the fetcher write `admin_action`. In `email_outbox` an app role queues only new `pending` rows to its own side (`app_candidate` and `app_fetcher` candidates, `app_portal` portal users or invites, `app_admin` anyone). A `dedupe_key` sent by an app role is stored as `<role>:<key>` in `email_outbox` and `notification`, so `on conflict do nothing` works within a role and no role can take another's key. App code that looks a row up by key must add the prefix. Rows written by the owner's functions keep their key.
- **The public API stays shut.** Supabase's Data API is off. Every migration revokes rights from `anon`, `authenticated`, `service_role` and PUBLIC on tables and functions. Extensions go in schema `extensions`. `pg_graphql` is dropped.
- **Launch B is locked three ways (#72):** a `feature_flag` row; no grants on Launch B tables or functions until a named person runs that migration (#113); and two CHECKs on Launch A tables (`job.application_route = 'own_page'`, `candidate_profile.visible_to_employers = false`) that the same migration drops.
- **Delete actions.** Every foreign key states its delete action. Erasing a candidate cascades to their owned rows and sets null on shared records. A job with saved, tracker, application, case, report or strike rows cannot be deleted. `audit_event` and `email_outbox` hold person ids as plain text with no foreign key, so a log row never blocks a deletion.
- **Paging (#125):** next and previous only, keyed on the sort key plus `id`. Never `OFFSET`. Counts stop at 200. Every list query lives in the Search module and names its columns (never `select job.*`). The Search module is `packages/db/src/search.ts`: `listJobs` (three sorts: sponsor, newest, salary; opaque cursors; the first page carries the capped count) and `getJob` (one live job with its advert, employer, badges, last checked and the rules date). **Filters (S1, S2, #247):** `listJobs(db, { sort, after, before, filters })` takes `q` (keyword, `websearch_to_tsquery('english', q)` on `search_vector`, the writers' config; trimmed, at most 200 characters, control characters refused; a query of only stop words or punctuation is no keyword filter), `occupationCode`, `sector`, `county`, `salaryMin`, `badge` (the alert filters, one check `checkJobFilters` that `checkAlert` also runs, with the alert run's meaning in 0024: `salaryMin` means the job states pay and `salary_sort >= salaryMin`), `postedWithin` (1, 3, 7 or 30 days) and `salaryStated` (`num_nonnulls(salary_low, salary_high) > 0`). Absent means any; every value is a parameter. `parseSearch(URLSearchParams)` reads them from a page URL (an empty value means any, a key given twice is refused, unknown keys such as `sort` or tracking tags are ignored) and `searchParams` writes them back. Bad input throws `BadSearchInput`. A cursor carries a hash of its filters, so a cursor from another filter set (or none) is refused. The keyword is matched once on `job_live_search` in a materialized CTE and a keyword cursor page walks ids only, so no plan reads `search_vector` row by row. `toAlertBody(filters)` gives the body `checkAlert` takes; it leaves out `q`, `postedWithin` and `salaryStated`, which an alert has no accepted field for (the alert route refuses free text), so the alert then matches more than the search. With the same five filters a search lists the jobs the alert run sends, except that the run skips full-quota jobs and sends only jobs new since its last run. `sectorCounts(db)` gives each of the six sectors with its live job count, zero included. Migration 0030 adds `job_live_sector_sponsor` and puts `salary_low`, `salary_high` in `job_live_sponsor` and `job_live_newest`; the budgets are in `test/perf/search.perf.ts`. The key rolls over on 1 January only when the refresh next runs (an import or a link change).
- **The fetched-job admin queue (#166 to #168)** is `packages/db/src/admin-queue.ts`, run as `app_admin`: `listQueue(db, staff, { after })` (open and claimed `fetched_job` items, oldest first, next-page cursor) and `getItem(db, staff, id)` (one item with its advert text), both of which refuse a staff member who is not active or lacks `fetched_job_reviewer` (step 13d, #234 D7), `claim`, `release`, `approve` and `reject`. A claim older than 24 hours, or held by someone no longer active, is taken over by the next `claim`; `release` gives an item back to open (claimer only). Each takeover and release writes one audit row (`fetched_job.take_over`, `fetched_job.release`). Each action takes the acting staff id, refuses it unless it is an active `staff_user` holding the `fetched_job_reviewer` role (checked in the same statement, no other role stands in; refusal `not_active_staff` first, then `not_reviewer`, #193), and sets `app.staff_user_id` for its transaction. Only the claimer decides, under row locks on the item and the job. Approve re-runs `assess` on the saved title, employer, county and advert text with the staff member's occupation code (and pay and contract, if given); only a `stated_pay` or `big_company` pass with no scam wording goes live, with the columns the fetcher writes. Reject closes the job as `removed`. Each decision writes one `admin_action` audit row (`fetched_job.approve` or `fetched_job.reject`, a reason code, no free text).
- **The held employer and agency job queues (step 15 Q1, #244)** are `packages/db/src/job-queues.ts`, run as `app_admin`, over the `scam_flag`, `post_strike_job_review` and `agency_client_check` items of employer and agency jobs (a `scam_flag` item the fetcher wrote on a fetched job is not shown or decided here). Roles: `scam_flag` is decided by `trust_and_safety`, the other two by `account_reviewer`, and an `administrator` may act on all three (the engineer's choice for these queues; in the fetched queue no role implies another). Every call checks the role first, reads included (`not_active_staff`, then `not_reviewer`). `listJobQueue(db, staff, queue, { after })` (open and claimed items of one queue, oldest first on `review_item_queue_idx`, the fetched queue's cursor; an unknown queue is `bad_queue`), `getJobQueueItem(db, staff, id)` (one item with the job's fields, the company, its restriction, the client name and check, the item's reason and the advert text), `claimJobItem`, `releaseJobItem` (claim, stale take-over and release as in the fetched queue, audited as `<queue>.take_over` and `<queue>.release`), `approveJobItem` (the item is `done`, outcome `approved`; the job moves `in_review` to `live` only when no other open or claimed item of the three queues is left on it, otherwise it stays in review; one `<queue>.approve` audit row on the job either way; the job's own guards still apply, so a company that is no longer verified is `company_not_active`, and approving a post-strike job does not lift the company's restriction) and `rejectJobItem` (a reason code; the item is `done`, outcome `rejected`, one `<queue>.reject` audit row, and the job closes with `close_reason = 'removed'`, which `job_queue_review` turns into dropping the job's other open items, all in one transaction). Only the claimer decides, under row locks on the item and the job, and the job must still be `in_review` (`job_not_in_review`). Route: `/api/employer-jobs`.
- **Periods are settings.** Nothing stores a delete date. `run_retention` works dates out from `setting`. The audit log period is the one exception.
- **Pooler.** Apps connect through Supabase's transaction-mode pooler: pass no statement name (`prepare: false`), use no `set` without `local`, no advisory locks, no `listen`.
- **Login pools (#97).** Candidate, portal and staff each have their own Better Auth tables, renamed with `modelName` and with camelCase fields mapped to lowercase. Added status columns are declared with `input: false`, and Better Auth does not enforce them, so the Identity module refuses suspended, blocked, disabled and deleted people on every request. Rate limits are stored in the database. Staff sign-up is off.
- **Staff login (#169 to #172).** The admin app serves the staff pool at `/api/auth/staff/*` (`apps/admin/app/api/auth/staff/[...all]/route.ts`) and connects with `DATABASE_URL`, the `app_admin` login. It also needs `STAFF_AUTH_URL` (the admin site's https address; http only for localhost) and `STAFF_AUTH_SECRET` (at least 32 random characters); a request with either missing or bad fails closed. Every admin call starts with `requireStaff(headers)` from `apps/admin/lib/staff.ts`: it refuses no session and anyone whose `staff_user.status` is not `active`, even with an open session, and returns the staff id the admin queue functions take. A staff session ends after 8 hours without use (Better Auth's `expiresIn` 8 h, `updateAge` 5 min, so it ends 7 h 55 min to 8 h after the last use); candidate and portal sessions keep Better Auth's defaults. Staff email is not set up yet, so a reset request sends nothing. The first logins are made by the owner with `DATABASE_URL_MIGRATE=... node packages/db/src/staff-seed-cli.ts <email> "<name>" <role>[,<role>...]`, which asks for the password twice without showing it (at least 12 characters) and, in one transaction as `portal_owner`, writes the `staff_user`, its credential `staff_account`, the roles with `seeded_by_owner = true` and one `staff.seed` audit row. It refuses an existing email, an unknown role and any login that cannot act as `portal_owner`.
- **Candidate login (#174 to #178).** The candidate app serves the candidate pool at `/api/auth/candidate/*` (`apps/candidate/app/api/auth/candidate/[...all]/route.ts`, no pages yet) and connects with `DATABASE_URL`, the `app_candidate` login. It also needs `CANDIDATE_AUTH_URL` (`http://localhost:3000` for now) and `CANDIDATE_AUTH_SECRET` (at least 32 random characters); either missing or bad fails closed. Email goes to the fake sender in `packages/auth/src/fake-email.ts`: it keeps each email in memory (tests read the link), prints the link to the terminal, and refuses to start for any address but localhost or 127.0.0.1, so a deploy cannot quietly send nothing until a real email service is wired in. Sign-up needs `needsPermit`, `over18` and `acceptsTerms`, each exactly `true`; a plugin checks them before the route runs (so an existing email is refused the same way as a new one), and a database hook writes one `consent_record` (purpose `signup_terms`, the current text, the answers in `details`) through the `candidate_consent_record` view inside Better Auth's own sign-up transaction, so no account exists without it. Sign-up refuses with 503 while no `signup_terms` text exists. Save the placeholder wording once, with two different staff ids (the proposer holds any role, the confirmer is an administrator): `DATABASE_URL=<app_admin connection> node packages/db/src/signup-terms-cli.ts <proposer staff id> <confirmer staff id>`; it makes the approval request, confirms it as the other person, saves the text `placeholder-2026-11-12`, and is safe to run twice. With `--portal` first (`node packages/db/src/signup-terms-cli.ts --portal <proposer> <confirmer>`) it saves the employer and agency placeholder instead (purpose `portal_signup_terms`, same version name); each purpose is checked on its own. A candidate session lasts 7 days (Better Auth's default). **Google sign-in (#179)** is on only when both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set (read from the environment, never from a file in the repo); with either missing the Google routes answer "provider not found". Its redirect address is `http://localhost:3000/api/auth/candidate/callback/google`. The client sends the three answers as `additionalData` on `POST /api/auth/candidate/sign-in/social` (`{"provider":"google","callbackURL":"/","additionalData":{"needsPermit":true,"over18":true,"acceptsTerms":true}}`). For a new person the user-create step reads them back from Better Auth's sign-in state and runs the same `checkSignup` as email sign-up (missing or wrong answers: no account, no consent row, redirect to the error address with `error=SIGNUP_ANSWERS_REFUSED`); it also refuses an email Google has not verified (`EMAIL_NOT_VERIFIED_BY_PROVIDER`), and a Google account is created email-confirmed. The consent row is then written by the same account-create hook, inside the same transaction. A person who already has a candidate account signs in without answers and no second consent row is written. Account linking is Better Auth's safe default, written out in `createAuth`: Google joins an existing email-and-password account only when Google says the email is verified and that account's email was confirmed here; an unconfirmed account is not joined (`error=account_not_linked`), and no provider is trusted on its own word. Only the candidate pool has Google.
- **Employer and agency login (#184 to #191).** The portal app serves the portal pool at `/api/auth/portal/*` (`apps/portal/app/api/auth/portal/[...all]/route.ts`; email and password only, no Google, #190) and connects with `DATABASE_URL`, the `app_portal` login. It also needs `PORTAL_AUTH_URL` (`http://localhost:3001` for now) and `PORTAL_AUTH_SECRET` (at least 32 random characters); either missing or bad fails closed. Email goes to the same fake sender as the candidate pool; the email must be confirmed before sign-in (#54), and a session lasts 7 days (Better Auth's default, #189). Sign-up needs `acceptsTerms`, exactly `true` (#188, #194): a plugin checks it before the route runs (so an existing email is refused the same way as a new one, `SIGNUP_ANSWERS_REFUSED`), and the `portal_consent_record` row (details `{"acceptsTerms":true}`) is written in the sign-up transaction, on the newest `portal_signup_terms` text, so a failed write undoes the login. With no such text sign-up answers 503 `SIGNUP_TERMS_MISSING`. Every portal call starts with `requirePortal` (`packages/auth`), which refuses no session and a blocked or deleted login and returns the active membership with its organisation, or `membership: null` for a login with no company; such a login can only become a company's owner, through `POST /api/portal/claim` `{"organisationId": "n"}` (the id as a string of digits, as every id the portal sends and takes) (calls `claim_organisation`: `verified` when the email domain is that company's `organisation_domain` and no other's, otherwise `pending_review` plus an `account_review` item) or `POST /api/portal/register` `{"kind": "employer" | "agency", "displayName", "croNumber"?, "wrcLicenceNumber"?}` (calls `register_organisation`, always `pending_review`). Both take the user id from the session only, refuse any unknown field, a body over 2,048 characters and an `Origin` that is not the portal's own, allow 5 calls in 10 minutes per login, and answer refusals with short codes (`BAD_ORIGIN`, `BODY_TOO_LARGE`, `BAD_REQUEST`, `NO_SESSION`, `REFUSED`, `EMAIL_NOT_VERIFIED`, `ALREADY_IN_A_COMPANY`, `ORGANISATION_NOT_AVAILABLE`, `NUMBER_ALREADY_REGISTERED`, `TOO_MANY_REQUESTS`). The ban check happens there, at claim and registration time, not at sign-up (#191): a banned email domain or company number gets the plain `REFUSED` a blocked login gets, so the reply names no ban. A company-number ban can still be inferred when claiming: the ban check comes before the "is it unclaimed" check, so for a company that is not unclaimed the reply is `REFUSED` if its number is banned and `ORGANISATION_NOT_AVAILABLE` if not (register behaves the same with `NUMBER_ALREADY_REGISTERED`). The email-domain ban cannot be probed this way. The codes are unchanged; changing them waits for an owner decision.
- **Teams (#52, #103, #130, #132, migration 0013).** `GET /api/portal/team` returns the caller's team: every active member sees the members (name, email, role, signer switch); only the account owner also sees open invites (with their expiry) and join requests; a login with no company gets `{"team": null, "joinRequest": ...}` (its own open request, or null). `POST /api/portal/team` takes `{"action", ...}`: `invite` `{email, role, isSigner}` (owner; role viewer, poster or recruiter), `accept` `{token}`, `request` `{organisationId}`, `approve` `{membershipId, role, isSigner}` and `refuse` `{membershipId}` (owner, a join request; ids as strings of digits), `remove` `{membershipId}` (owner, a member or an invite), `leave` `{}` (a member, or a login withdrawing its request), `role` `{membershipId, role, isSigner}` (owner), `transfer` `{membershipId}` (owner). It makes the same checks as claim and register in the same order (portal `Origin`, 2,048-character body, unknown fields refused, session) and allows 20 team calls in 10 minutes per login. `accept`, `request` and `leave` work for a login with no company. The invite makes 32 random bytes, sends the link `PORTAL_AUTH_URL/team/accept?token=...` through the portal's email sender (the fake one until 8.1b) and passes only the sha256 to `team_invite`, all in one transaction, so a failed send leaves no invite (`EMAIL_FAILED`, 502). Refusal codes: `BAD_ORIGIN`, `BODY_TOO_LARGE`, `BAD_REQUEST`, `NO_SESSION`, `REFUSED` (blocked, deleted, banned email domain, or any refusal not listed, #191), `EMAIL_NOT_VERIFIED`, `NOT_OWNER`, `NOT_A_MEMBER`, `MEMBER_NOT_FOUND` (also another company's id), `TEAM_FULL`, `ALREADY_IN_TEAM`, `ALREADY_IN_A_COMPANY`, `INVITE_NOT_VALID` (wrong, used, expired or another email's token, one code for all), `NOT_ALLOWED_DOMAIN`, `OWNER_MUST_TRANSFER`, `VIEWER_NOT_SIGNER`, `ORGANISATION_NOT_AVAILABLE`, `TOO_MANY_REQUESTS`, `EMAIL_FAILED`.

- **Stored files (step 15, no migration).** CVs (`candidate_cv`) and case document copies (`case_document`, through `candidate_case_document` and `portal_case_document`) are kept in the private S3 bucket `irish-job-portal-files` (`eu-west-1`, versioning off, public access blocked) under random keys (`cv/<uuid>`, `case/<uuid>`), written and read by `packages/db/src/files.ts` through the store module `file-store.ts` (`aws4fetch`). The apps read `FILES_S3_KEY_ID`, `FILES_S3_SECRET`, `FILES_S3_BUCKET` and `FILES_S3_REGION` (never `AWS_*`); without them only the file routes answer 503. Routes: candidate `GET`, `PUT` (multipart field `file`, PDF or DOCX) and `DELETE /api/candidate/cv`, `GET /api/candidate/cv/download`; both sides `GET` and `POST /api/<candidate|portal>/cases/<id>/documents` (PDF, JPEG or PNG, at most 20 stored copies a case, refused once the case is `decision` or `closed`) and `GET .../documents/<docId>`. A download is a 302 to a 60-second presigned link that downloads, never renders. The bytes decide the type (`file-check.ts`); the cap is 4 MB. Uploads also count against 10 an hour per login (`upload:<id>` in the app's own rate-limit table). The daily retention run removes the objects for every key the rules return and goes red only when a removal fails. The key never appears in an answer except inside the presigned link.
- **Candidate data export (step 15, migration 0025).** `GET /api/candidate/export` on the candidate site answers the signed-in candidate's own data as one JSON file (`exportData` in `packages/db/src/candidate.ts`). Statement one reads the candidate tables and writes one `audit_event` row (kind `data_access`, action `candidate.export`, the candidate as actor and subject); statement two calls `private.candidate_export_extras(candidate id)`, a `security definer` read for `app_candidate` only (which gets `usage` on schema `private` for it), because the role has no select on `audit_event` or `email_outbox` and there is no row level security. It returns for that one id: `emailsWeSent` (template, status, send_after, sent_at), `yourActionsOnTheSite` (kind, action, object_type, time; no before or after) and `whoAccessedOrReceivedYourData` (employer actor: the organisation names of the portal user's memberships; staff actor: the words "Portal staff"; system actor: "Portal system"). Like the other private functions it trusts the id the app passes from the session. `contactFormMessages` and `reportsYouMade` stay under `notIncluded` (the role reads only their ids).
- **Report a job (slice 8.5).** `POST /api/report` on the candidate site and `POST /api/portal/report` on the portal (`packages/db/src/report.ts`, `handleReport`): `{"jobId": "n", "reason": "asks_for_money" | "no_sponsorship" | "job_closed" | "wrong_details" | "other", "evidence"?: "..." (1 to 2,000 characters)}`, the reporter from the session only, the job must be live, 10 reports an hour per login, one open report per login and job. The answer is only `{"ok": true}` or a code (`BAD_ORIGIN`, `BODY_TOO_LARGE`, `BAD_REQUEST`, `NO_SESSION`, `REFUSED`, `TOO_MANY_REQUESTS`, `JOB_NOT_FOUND`, `ALREADY_REPORTED`).
- **The contact form (decision #55, no migration).** `POST /api/contact` on the candidate site and `POST /api/portal/contact` on the portal (`packages/db/src/contact.ts`, `handleContact`): `{"topic": "general" | "account" | "data_request" | "other", "name": "..." (1 to 120), "email": "..." (an address, up to 254), "body": "..." (1 to 5,000 characters, newline and tab allowed, no other control or format character)}`. Unknown fields are refused. The candidate route is open to visitors, who must give name and email; a signed-in candidate's id comes from the session only and name and email may be left out (the account's are used); a suspended or deleted candidate is treated as a visitor. The portal route needs a portal login (any active one, with or without a company). Limits: 5 an hour per login, and for a visitor 5 an hour per client address (`x-vercel-forwarded-for`) and 5 an hour per lower-cased email (an HMAC in the key, never the address), all through `withinRate`. The answer is only `{"ok": true}` or a code (`BAD_ORIGIN`, `BODY_TOO_LARGE`, `BAD_REQUEST`, `NO_SESSION`, `REFUSED`, `TOO_MANY_REQUESTS`), the same whether or not the email has an account. The bot check goes in `handleContact` at the line marked `BOT CHECK GOES HERE`. A `data_request` message gets its review item from the trigger.
- **Public reads, visitor cap and read limit (S3, S5, #46, no migration).** The candidate site's public GETs: `/api/jobs` (list and search: `sort`, `after` or `before`, and the `parseSearch` filters), `/api/job?id=` (one live job), `/api/company?slug=` and `/api/occupation?code=` (the pages with their live jobs, `after`). Each is one line over `publicRead` in `packages/db/src/public-read.ts`, which reads the session first (`signedInCandidate`). A visitor is anyone without a live candidate session: no cookie, a forged or expired one, a suspended or deleted candidate, or a portal or staff cookie. ## Tables

Launch A unless marked. "Pool" tables are the five Better Auth tables of a login pool.

### Jobs

- `job`: one advert, whatever its source. `organisation_id` is who stands behind it (strikes fall there, including agency jobs, #89). Status moves draft, in_review, live, under_review, hidden, closed. `permit_type` is required, fetched jobs are always critical_skills (#42). The write guard trigger limits what each role may change, and `posted_at` is set by trigger, never by a role. The fetcher never moves a job back to draft, never changes the close reason of a closed job, and reopens a closed job, to live only, when it expired or the fetcher closed it, as `closed`, `recheck_failed` or `source_stale` (never one staff removed). The close reason `recheck_failed` (migration 0006) is for a live fetched job that fails a later check; a check allows it on fetched jobs only. The close reason `source_stale` (migration 0035) is for a live fetched job whose board had no good fetch for 7 days (`docs/job-rules.md`, stale-board close); also fetched jobs only, and the fetcher may reopen it to live like `closed` and `recheck_failed`. List indexes are partial on `status = 'live'` and lead with `(not quota_full)`. `permit_history` is copied from the organisation by trigger. A visitor has no table. Their reports and contact messages are rows with no account attached.

- `contact_request` (Launch B): an employer asks a visible candidate for contact (#41, #47). Insert trigger enforces visibility, daily limit and re-ask gap.

  Why it is sensitive: `claim_organisation` (latest text in migration 0022) verifies a claim with no staff review when the claimant's confirmed email domain is one of the company's domains and no other company's, so a wrong domain hands the company to a stranger. Every domain saved passes `domainProblem` (`packages/db/src/domain-check.ts`): a plain lower-case ASCII host name of two or more labels (no scheme, path, port, space or upper case), labels of at most 63 characters, not an IP address, no punycode (`xn--`) label (a look-alike of a real name), and not on `FREE_EMAIL_DOMAINS`. Remove is refused `open_ban_case` (409) while the company has an open case (undecided, a decision or ban waiting for its second person, or an appeal waiting) opened after that domain was added, because the ban of that case takes the domains from before it opened (`ban_matches_case`, `BAN_DOMAINS`); a domain added after the case opened is never banned by it, so it can go. Each add and remove writes one `audit_event` row in the same statement (`organisation_domain.add` / `.remove`, object the organisation, the domain and source in `after` / `before`, the reason code, source `panel`).

The file is tab-separated `display_name, domain, evidence_url, evidence_quote`. A wrong header, a line without 4 columns, over 2,000 rows or 1 MB refuses the whole file. A line is refused alone when its domain fails `domainProblem`, its evidence link is not one `https` address, its quote is empty, no company (not merged away) has that exact display name or two do, the file gives the domain to two companies, or another company has it already (named). In one transaction of 6 statements whatever the size (`packages/db/test/company-domains.test.ts`, budgets): rows written with `source = 'seed'` and one `organisation_domain.seed` audit row each (actor_system `domain_seed`, the evidence link in `after`). ## Callable functions

All are `SECURITY DEFINER`, owned by `portal_owner`, in schema `private`, with execute revoked from PUBLIC. Each writes its own `audit_event` rows in the same transaction. Trigger functions also live in `private` and are granted to no role.

- `erase_candidate(id, on_request)`: erases a candidate. Refuses (and returns the reason) while they have an open services case or are the target of an open report. Empties applications, turns consents into bare proof, deletes owned rows and login rows, calls `audit_pseudonymise`. Returns the storage keys of files to delete. Executed by `app_admin`.
- `erase_portal_user(id, on_request)`: the same for a portal login. Also refuses an account owner who still has other active members. Executed by `app_admin`.
- `run_retention()`: runs one batch (up to 1,000 rows) of the first retention rule with rows due, and returns that rule's key and how many rows are left. The admin app's scheduled route calls it in a loop, one transaction per call. Rules are listed in `private.retention_rules()`. Executed by `app_admin`.
- `audit_pseudonymise(id)`: replaces a person's id in the log with a random stand-in. Called only by the two erase functions. No app role.
- `audit_purge()`: deletes audit rows older than the `audit_event` setting (0041; empty deletes nothing). Nothing schedules it: retention rule 44 does the same job daily. Run by the named person as `portal_owner` if needed. No app role.
- `approval_request_due()`: returns the approval request ids that retention may delete. Used by `run_retention`.
- `claim_organisation(portal_user_id, organisation_id)`: a verified person claims an existing organisation, in one conditional update. Executed by `app_portal`. Since migration 0016 (#203) it also refuses, with `COOL_DOWN`, the same login claiming the same company within 24 hours of a rejection (the login's removed owner membership and that company's `rejected` account_review item share the rejecting transaction's instant; a claim that lapsed unanswered is not a rejection).
- `answer_review(portal_user_id, note)` (migration 0016, #197): the active account owner of a `needs_info` company sends a note of 1 to 1,000 characters (no control or format characters). It is stored in the company's open account_review item as `detail.answer` and `detail.answered_at` (never in the audit log, #182), the company becomes `pending_review`, and one `organisation.answer_review` audit row of codes is written. A reviewer asking for more again clears the old answer. Refusals: `REFUSED` (not the owner, or a blocked login), `NOT_WAITING` (not `needs_info`, or no open item), `BAD_REQUEST` (the note). Executed by `app_portal`; the route is `POST /api/portal/review-answer`.
- `register_organisation(portal_user_id, kind, display_name, cro_number, wrc_licence_number)`: sign-up for a first-time sponsor or an agency. Always pending review. It cleans the typed number first (CRO: spaces and a leading IE removed, leading zeros dropped; WRC: spaces removed, upper case, EA added to bare digits, #210) and writes the register result into the account review item detail: `register`, `found`, `name_matches` (compared on the normalised name, so "Acme Ltd" matches "ACME LIMITED"), `status` (CRO only) and `possibly_lapsed` (WRC only). A number not in the register still goes to review, marked not found; nothing new is refused. Executed by `app_portal`.
- The team functions (migration 0013), all executed by `app_portal`, each taking the acting login's id from the session. Each locks the organisation row (`for no key update`) and reads its rows again before checking, so two changes to one team run one after the other; `team_accept` and `team_request` also lock the login's row. Each writes one `audit_event` row (`security`, action `membership.<verb>`, codes only, no email). A refusal raises `team refused: CODE`. The limit counts active members, live invites and join requests against `organisation.member_limit` (expired invites are dropped first). Companies that take on people are `pending_review`, `needs_info`, `verified` and `verified_restricted`.
  - `team_invite(user, email, role, is_signer, token_hash)`: the active owner invites an email (not banned, not the owner's own, not a member, a join request or a live invite of this team) as viewer, poster or recruiter; a viewer is never a signer. Expires after 7 days.
  - `team_accept(user, token_hash)`: a confirmed login whose email is the invite's accepts a live invite (not banned, not already in a company, #130). It becomes active with the invite's role and switch; its own join requests elsewhere are dropped.
  - `team_request(user, organisation_id)`: a confirmed login with no membership and no open request asks to join a company that takes on people. Its email domain must be one of the company's `organisation_domain` rows, and not banned.
  - `team_answer(user, membership_id, approve, role, is_signer)`: the owner approves (active, with the role and signer switch the owner picks; a viewer is never a signer) or refuses (removed) a join request; approval rechecks the requester (not blocked, deleted or banned).

  - `team_leave(user)`: a member leaves, or a login withdraws its join request. The owner may leave only as the last active member; then the company's open invites and requests are removed too, and the company itself stays as it is (#132).

## Backups

Supabase Free gives no backup we can download, so we make our own (#115, #126, step 15).

- **What:** `.github/workflows/backup.yml` runs `packages/db/src/backup-cli.ts` as `app_backup` every 6 hours (00:47, 06:47, 12:47 and 18:47 UTC, `47 */6 * * *`, O1; GitHub may start it late) and by hand ("Run workflow"). It exports one snapshot, counts every table of `public`, `private` and `drizzle` in it, and runs `pg_dump` 17 (custom format) on that same snapshot, so counts and dump are the same moment. It writes `db-<UTC yyyymmddThhmmZ>.dump` and `.json` (the manifest: format version, time, server and `pg_dump` versions, the row count of every table, the migration hashes, the dump's size and SHA-256), and uploads both to `s3://irish-job-portal-backups/db/<yyyy>/<mm>/` (eu-west-1), the dump first.
- **Left out:** the rows of `public.cro_company` (88 MB of 191 MB, re-imported every week from the register by `weekly-registers.yml`; the table definition and its indexes are in the dump, the manifest marks it "data not included"). Also left out: `auth`, `storage` and the other Supabase schemas (nothing of ours lives there), and files in the files bucket (S3 keeps those).
- **Four a day:** the names carry the minute (`db-20261118T0647Z`), so runs never overwrite each other, the restore check's "newest" is the last name in sorted order, and the 30 day lifecycle rule expires by age, not by count: nothing assumes one dump a day. The bucket holds about 120 dumps at once.
- **Restore check:** `.github/workflows/restore-check.yml` (the 1st of each month, 04:37 UTC, or by hand) downloads the newest backup, restores it with `pg_restore --exit-on-error --no-owner` into a fresh container of the test image, and checks the SHA-256 and size, every table's row count against the manifest (`cro_company` must be 0), the recorded migrations against the repo's files (the backup may be behind the repo, never ahead or different), and that the backup is under 48 hours old. A red run means the backup cannot be trusted.
- **By hand:** start a throwaway server (`npm run db:test:up`), download a dump and its manifest from the bucket, then
  `RESTORE_ADMIN_URL=postgres://postgres:test@127.0.0.1:54329/postgres PG_TOOLS_PREFIX="podman exec -i -e PGPASSWORD portal-test-db" PG_TOOLS_ADDR=127.0.0.1:5432 DATABASE_SSL=disable node packages/db/src/restore-check-cli.ts --dump db-X.dump --manifest db-X.json`
  (add `--any-age` for a file older than 48 hours, `--keep` to leave the restored database to look at). The target must be an empty throwaway server, never a real database. A real recovery restores the same file with `pg_restore` without `--no-owner` into a database where the roles exist. On a Supabase project it runs as `postgres`, which may not set `supabase_admin`'s default privileges (the project has them already): list the dump with `pg_restore --list`, drop the `DEFAULT ACL ... supabase_admin` lines, and restore with `--use-list`, as the restore check does (`restoreList`).
- **In the AWS console, not in code:** the bucket's versioning and its lifecycle rule `expire-old-backups` (30 days, a placeholder until the solicitor's retention periods, #99), and the IAM user `job-portal-backup` (put, get and list on that bucket, no delete). GitHub secrets: `BACKUP_DATABASE_URL` (the `app_backup` pooler string), `BACKUP_S3_KEY_ID`, `BACKUP_S3_SECRET`.
- **In tests:** `packages/db/test/backup.test.ts` backs up a seeded database and restores it; `PG_TOOLS_PREFIX` and `PG_TOOLS_ADDR` say where `pg_dump` and `pg_restore` run (inside the test container; `check.yml` sets them for its service container).
